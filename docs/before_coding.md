# コーディング開始前に決めること

> **このページは、チームで最初のコードを書き始める前に必ず全員で読む。**
> ここで決める 3 つを飛ばして「とりあえず動くものを作ってから考えよう」で始めると、
> 結合の週に作り直しが発生してスケジュールが破綻する。

チーム開発で時間を溶かす原因は、技術力よりも**分担の切り方**と**つなぎ目の未定義**にある。
逆に言えば、この 2 つを最初の 1〜2 回のミーティングで決めておくだけで、
あとは各自が自分の担当に集中できる。

決めることは 3 つ。

| # | 決めること | 記入する場所 |
|:-:|---|---|
| ① | **担当範囲**をコンポーネント単位で切る | [`design/assignments.md`](design/assignments.md) |
| ② | **コンポーネント間のデータフォーマット**を確定する | [`design/interfaces.md`](design/interfaces.md) |
| ③ | **リポジトリに入れてよいもの / ダメなもの**を全員で合意する | このページの対応表 |

---

## ① 担当範囲は「コンポーネント単位」で切る

### やってはいけない切り方

- ❌「`main.cpp` の前半を A さん、後半を B さん」
- ❌「この関数は A さん、あの関数は B さん」
- ❌「とりあえず手が空いている人が空いているところをやる」

**プログラムの行やファイルの中を分割して担当を割り振ってはいけない。**
同じファイルを 2 人が同時に編集すると、毎回コンフリクト（衝突）が起き、
解決のたびに誰かの変更が消える事故が起きる。しかも「どこまでが自分の責任か」が
曖昧なので、バグが出たときに誰も直せない。

### 正しい切り方

**コンポーネント** = 「入力と出力を言葉で説明でき、**相手がいなくても単独で動作確認できる**塊」。

こう切る。

- ✅「マイコン側のファームウェア = A さん」
- ✅「PC 側のアプリ（受け取ったデータを画面・音にする）= B さん」
- ✅「扱うデータそのもの（マップ / 楽譜 / シナリオ / 設定値）= C さん」

例えばセンサ機器の開発なら「ファームウェア」「PC アプリ」「データ」の 3 コンポーネントに割れる。
Web アプリなら「フロントエンド」「API サーバ」「DB スキーマ」。ゲームなら
「ゲームロジック」「描画・UI」「ステージデータ」。

### 切れているかの判定テスト

その担当を切り出したとき、次の質問に「はい」と答えられるか。

1. **入力と出力を 1 行で説明できるか**（例:「ボタンの押下を受け取り、通信パケットを送る」）
2. **相手の実装がまだ無くても、ダミーデータで動作確認できるか**
3. **担当ごとに触るディレクトリが分かれているか**

3 番目が重要。担当をディレクトリで分けると、**物理的にコンフリクトしなくなる**。
このテンプレートの `firmware/` `pc_app/` `assets/` `tools/` という分け方は、
まさにこの「担当ごとにディレクトリを分ける」ための例として置いてある。

### 決めたら書く

[`design/assignments.md`](design/assignments.md) に担当表を記入する。
**「未定」が 1 つでも残っている状態でコードを書き始めない。**

## ② コンポーネント間のデータフォーマットを先に確定する

担当を切ると、必ず**つなぎ目（インターフェース）**ができる。
「ファームウェアが送るデータを、PC アプリが受け取る」の"データ"の部分だ。

**このつなぎ目の形式を、コードを書き始める前に確定させる。**

### なぜ先に決めるのか

つなぎ目さえ決まっていれば、**中身は各自が好きに書ける**。
A さんが送信側をどう実装しようが、B さんが受信側をどう実装しようが、
決めた形式で受け渡しできれば結合は一発で通る。

逆に、決めずに書き始めると必ずこうなる。

- A さんは「センサ値をそのまま送る」つもりで実装した
- B さんは「0〜100 に正規化された値が来る」つもりで実装した
- 結合の日に初めて発覚し、どちらかが書き直す（しかも締切直前）

### 何を決めるのか

つなぎ目 1 つにつき、最低これだけ決める。

| 項目 | 例 |
|---|---|
| **何を**（フィールド名） | `timestamp`, `sensor_id`, `value` |
| **どの型で** | 符号なし 32bit 整数 / 文字列 / 浮動小数 |
| **どの単位で** | ミリ秒 / メートル / 0〜1023 の生値 |
| **どの範囲・精度で** | 0〜1023、小数第 2 位まで |
| **どの頻度で** | 20ms ごと / イベント発生時のみ |
| **どの経路で** | USB シリアル 115200bps / Wi-Fi UDP / JSON ファイル |
| **バージョン** | `v1`（変えたら番号を上げる） |

### 決めたら書く、そして口頭で変えない

[`design/interfaces.md`](design/interfaces.md) に記入する。

**確定したフォーマットを変えるときは、必ず PR で変更する。**
「さっき口で言ったやつ、やっぱりこう変えたから」は事故のもと。
PR にすれば、影響を受ける全員に通知が飛び、記録も残る。

### 決めた直後にやると効くこと

**ダミーデータ（サンプル）を先に作って、リポジトリに置く。**

決めた形式のサンプルデータが 1 個あれば、受け取る側は送信側の完成を待たずに
自分のコードを動かせる。待ち時間がゼロになるので、これは非常に効く。

- 通信なら → サンプルのパケット列 / ログファイル
- データファイルなら → 数行だけのサンプルファイルを [`assets/examples/`](../assets/examples/) へ

## ③ リポジトリに入れてよいもの / ダメなもの

### 前提：チーム開発リポジトリは「いつ public になっても平気」な状態で運用する

授業では、最後に成果物を教員・TA に見てもらう場面がある。
private リポジトリのままだと閲覧してもらえず、**提出直前に慌てて public 化**することになる。
そのときに個人情報や著作物が混ざっていると、履歴からは簡単に消せない。

なので**最初から「public 前提」で運用する**。これがこのテンプレートの前提思想。

public 前提で運用する利点は、慌てなくて済むことだけではない。

- **コミット履歴ごと見せられる**。「誰がいつ何をやったか」がそのまま作業の証拠になる
- Issue・PR のやり取りが、チーム開発をやった記録として残る
- 就職活動やポートフォリオでそのまま見せられる

### そのかわり、リポジトリは 2 つに分ける

public に置けないもの（個人レポート・授業資料・議事録など）は、
**別の private リポジトリ**にまとめて置く。そのための雛形も用意してある。

| リポジトリ | 公開設定 | 中身 | 元にするテンプレート |
|---|---|---|---|
| チーム開発リポジトリ | **public**（最初から public 前提） | コード・設計・チーム提出物 | このテンプレート |
| チーム内部リポジトリ | **private**（絶対に public にしない） | 個人レポート・授業資料・議事録 | [hackathon-template-private](https://github.com/takushio2525/hackathon-template-private) |

### 線引き表

| 種類 | どちらへ |
|---|:---:|
| ソースコード・`platformio.ini` などのビルド設定 | **public** |
| CI 設定（`.github/workflows/`） | **public** |
| 設計書・データフォーマット定義・ADR | **public** |
| 開発の運用規約（`CONTRIBUTING.md` など） | **public** |
| 自分たちで撮った回路写真・自作した図 | **public** |
| 個人レポート・個人提出物（氏名・学籍番号入り） | **private** |
| 授業の配布資料（スライド・課題 PDF・ルーブリック）＝著作権物 | **private** |
| 評価・成績に関わるもの（採点基準・評価シート・自己採点） | **private** |
| 議事録・チーム内の連絡・雑多なメモ | **private** |
| 人が写った写真・学内システムの画面キャプチャ | **private** |

### 迷ったときの判断ルール

> **氏名・学籍番号・著作権物・評価情報が 1 つでも入るなら private。**
> **公開されて困るか 5 秒迷ったら private。**

このルールだけ覚えておけば、ほぼ全部さばける。
「public に置いてよかったものを private に置いてしまった」は後から移せるが、
逆は履歴が残るので取り返しがつかない。**迷ったら private 側に倒す。**

### とくに見落としやすい 3 つ

**1. ファイル名にも学籍番号・実名を入れない**

`第1回議事録_<学籍番号>.pdf` のようなファイル名は、**ファイル名自体が個人情報**。
中身を伏せてもファイル一覧で丸見えになる。`誰が作ったか`はコミットの author で分かるので、
ファイル名には入れない。

**2. コミットの author メールアドレスは全部見える**

`git config user.email` に設定したメールアドレスは、**全コミットに刻まれて public で読める**。
大学から配布された学内メール（学籍番号がそのままアドレスになっていることが多い）を
設定すると、それが履歴に永久に残る。個人の Gmail か GitHub の noreply アドレスを使う。
設定方法は [CONTRIBUTING.md](../CONTRIBUTING.md#13-名前とメールアドレスを登録初回のみ) を参照。

**3. 個人のレポート作業を「ついで」に push しない**

個人レポートには、ほぼ確実に氏名・学籍番号・所属が書かれている。
チームリポジトリで作業していると「ついでにコミット」してしまいがち。
**最初から private リポジトリ側で作業する**のが唯一の確実な対策。

このテンプレートの `.gitignore` は、個人作業の置き場によく使われる名前
（`personal/` `個人/` `references/lectures/` など）を最初から除外してある。保険として効く。

### 機械でチェックする

人間の注意力に頼らないよう、**CI で秘匿情報スキャン**が動くようにしてある。

- 検査パターン: [`.github/secret-scan-patterns.txt`](../.github/secret-scan-patterns.txt)
- ワークフロー: [`.github/workflows/secret-scan.yml`](../.github/workflows/secret-scan.yml)

学籍番号らしき文字列・メールアドレス・API キーらしき文字列を検知すると PR が落ちる。
**自分たちの大学の学籍番号の形式に合わせて、パターンファイルを最初に調整すること。**

**引っかかったら、push する前に直す。**
一度 push してしまうと履歴に残り、消すには履歴の書き換え（全員の作業をやり直させる操作）が要る。

## 開始前チェックリスト

コードを書き始める前に、全員でこれを確認する。

- [ ] 担当表（[`design/assignments.md`](design/assignments.md)）が全部埋まっていて、「未定」が無い
- [ ] 担当ごとに触るディレクトリが分かれている
- [ ] つなぎ目のフォーマット（[`design/interfaces.md`](design/interfaces.md)）が確定している
- [ ] つなぎ目ごとにサンプルデータ（ダミー）が 1 個ある
- [ ] 線引き表（public / private）を全員が理解し、判断ルールを覚えた
- [ ] 全員が `git config user.email` を学内メール**以外**に設定した
- [ ] チーム内部用の private リポジトリを作り、全員を招待した
- [ ] [CONTRIBUTING.md](../CONTRIBUTING.md) のブランチ戦略とコミット規約に全員が合意した

全部にチェックが入ったら、コードを書き始めてよい。
