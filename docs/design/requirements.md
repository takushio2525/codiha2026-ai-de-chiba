千葉県の地図系サービスを 1 つに束ね、**住民と行政が相互に情報を投稿できる**ウェブサイト。

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| 名称 | **CHIZUBA**（**CHI**ba + **ZU**（地図）+ **BA**（場）） |
| 一言でいうと | 千葉県の地図系サービスを統括し、**住民と行政が相互に情報を投稿できる**ウェブサイト |
| 対応範囲 | **千葉県全域**（設計は市町村をパラメータ化する） |
| デモの範囲 | **市川市**（初期データ・デモシナリオを市川市に集中させる） |
| 2 本の柱 | **防災**（ハザードマップ・危険箇所報告・浸水報告・注意案内）と<br>**観光**（景観スポット・周遊ルート・おすすめ投稿） |
| 土台 | 既存の `app/`（Next.js + MapLibre の地図アプリ）の上に載せる |

### 何を解こうとしているか

千葉県・市町村のオープンデータは**公開された時点で止まっている**。
避難場所も AED も景観スポットも「市が持っている静的な一覧」であり、
**現場で今どうなっているか**（ガードレールが折れている・この道路が冠水している・
この時期はここが綺麗）は誰も更新できない。

CHIZUBA は、**オープンデータを土台に置いたうえで、その上に住民の投稿を重ね、
行政が応答できる場所**を作る。地図は既に共通言語になっているので、
防災と観光という性格の違う 2 つの用途を、同じ地図・同じ投稿の仕組みで扱える。

## 2. ユーザーロール

権限は 3 段階。**未ログインでも「見る」ことは全部できる**（防災情報を
ログインの壁の向こうに置かない）。投稿にだけログインを要求する。

| ロール | 誰か | できること |
|---|---|---|
| **未ログイン（閲覧者）** | 誰でも | 地図・ハザードマップ・全レイヤーの閲覧、投稿の閲覧、徒歩経路、注意案内の閲覧 |
| **一般ユーザー** | Google ログイン済みの住民・来訪者 | 上記 + **投稿**（危険箇所・浸水・観光おすすめ）、自分の投稿の編集・削除、他人の投稿へのコメント |
| **行政ユーザー** | 自治体職員（`role = 'gov'`） | 上記 + **行政コメント**（公式回答として区別表示）、**対応状況の更新**（受付／対応中／対応済）、**公式おすすめ投稿** |

- 行政ユーザーは**一般ユーザーの上位互換**。専用の管理画面は作らず、同じ地図画面の上で
  出せる操作が増える形にする（画面数を増やさず実装量を抑えるため）
- 行政の発言は**必ず視覚的に区別**する（バッジ＋色）。区別できないと
  「行政が言ったこと」と「住民が言ったこと」が混ざり、防災上の誤解を生む
- ロールの付与方法は [§8 認証](#8-認証) に書く

## 3. 機能一覧

チームで決めた要件 1〜8 を、そのまま機能 ID に落としたもの。
**ここに無いものは作らない。ここにあるものは全部作る**（順番は [§9](#9-実装順序) で決める）。

### 3-1. 防災

| ID | 機能 | 内容 | 依存 |
|---|---|---|---|
| **F-1** | ハザードマップ表示 | 洪水浸水想定・津波浸水想定・高潮浸水想定を地図に重ねて表示する。凡例と出典を出し、レイヤーごとに ON/OFF と不透明度を変えられる | 既存の地図土台 |
| **F-2** | 老朽化・危険箇所の市民報告 | 「ガードレールが折れている」「路面が陥没している」などを、**位置 + 写真 + 説明**で投稿する。地図上にピンで並び、誰でも閲覧できる | DB・認証・投稿基盤 |
| **F-3** | 雨天時の浸水状況報告 | 冠水している場所を、**位置 + 写真 + 説明 + 投稿時点の雨量**で投稿する。雨量は投稿時に自動で取得して記録に残す | F-2 の投稿基盤 + 気象データ |
| **F-4** | 蓄積データ × 雨予報にもとづく注意案内 | **過去に浸水報告があった地点**について、**雨の予報が出ているときに注意表示**を出す | F-3 の蓄積 + 気象予報 |

> **F-4 の表現について（重要な設計判断）**
> F-4 は「予測」ではなく「**過去にここで浸水報告がありました。雨の予報が出ています**」という
> **事実の提示**に留める。実装も UI 文言もこの線を越えない。
> 根拠のない浸水予測を出すことは防災上むしろ危険で、避難判断を誤らせるため。
> 「データが溜まるほど精度が上がる」という将来像は**プレゼンで語る**ものであって、
> 提出するコードが今できると主張するものではない。詳細は [§10 論点](#10-論点未決) 参照。

### 3-2. 観光

| ID | 機能 | 内容 | 依存 |
|---|---|---|---|
| **F-5** | 観光マップ | 景観スポットを地図に載せ、**一覧・徒歩ルート・解説**を出す。あわせて**お土産情報**を扱う | 既存の地図土台 + 経路 API |
| **F-6** | 観光おすすめの市民投稿 | 「ここが綺麗」「この店の◯◯が良い」を、F-2 と**同じ操作感**で投稿・共有できる | F-2 の投稿基盤 |

- **F-5 の主データは市川市「いちかわ景観100選」**（100 件全件に座標・日本語解説・英語解説あり）。
  文化財一覧 CSV は解説文が全件空なので**補助扱い**にする
- 解説文は最小 19 / 中央値 47 / 最大 88 文字と短い。**1〜2 文のキャプション**として扱い、
  「音声ガイド級の解説」を謳わない
- 景観100選 CSV の画像列は相対パスで解決できない（実測で全パターン 404）。
  **画像は使わない**前提で設計する
- **お土産情報**は市川市オープンデータに該当データセットが無いため、
  **F-6 の投稿カテゴリ「お土産」として住民投稿で集める**。これは実装量を増やさずに
  要件を満たすと同時に、「行政が持っていない情報こそ住民が持っている」という
  CHIZUBA のコンセプトの実例にもなる

### 3-3. 双方向性・基盤

| ID | 機能 | 内容 | 依存 |
|---|---|---|---|
| **F-7** | 行政からの応答 | 行政ユーザーが投稿に**公式コメント**を付け、**対応状況**（受付／対応中／対応済）を更新できる。行政発の**おすすめ投稿**もできる | 投稿基盤 + ロール |
| **F-8** | Google アカウントによるログイン | Google OAuth でログインする。**認証キーが未設定の環境では自動でデモログインに切り替わる**（[§8](#8-認証)） | — |

## 4. 設計判断: 3 種類の投稿を 1 つのモデルに統一する

### 結論: **統一する**

F-2（老朽化・危険箇所）・F-3（浸水）・F-6（観光おすすめ）は
**カテゴリ違いの同一投稿モデル**として 1 つのテーブル・1 つの API・1 つのフォームで扱う。

### 判断の根拠

3 つを並べると、**共通部分が本体で、差分は付随情報しかない**。

| 項目 | F-2 危険箇所 | F-3 浸水 | F-6 観光おすすめ |
|---|:---:|:---:|:---:|
| 位置（緯度経度） | ○ | ○ | ○ |
| 写真 | ○ | ○ | ○ |
| 本文 | ○ | ○ | ○ |
| 投稿者・投稿日時 | ○ | ○ | ○ |
| 市町村コード | ○ | ○ | ○ |
| 地図にピンで出る | ○ | ○ | ○ |
| コメントが付く | ○ | ○ | ○ |
| **固有の項目** | 危険の種別 | **雨量**・冠水の深さ | おすすめの種別（景観／お土産／飲食） |
| **行政の対応状況** | ○ | ○ | △（使わない） |

固有項目は**カテゴリごとに 1〜2 個**しかない。ここでテーブルを 3 つに割ると、
投稿 API・一覧 API・地図レイヤー・投稿フォーム・詳細パネルが**すべて 3 倍**になる。

審査のコード評価は「**実装した割合 × 正しく動作する割合**」の掛け算なので、
**同じ機能数をより少ないコードで実現するほど、動作割合が上がって有利**になる。
分けた場合の利点（カラムに型制約を効かせられる）より、この掛け算のほうが重い。

### どう統一するか

```
reports（投稿）
├── 共通カラム: id, category, title, body, lat, lon, city_code,
│               user_id, status, created_at, updated_at
├── details    : カテゴリ固有の項目を JSON で持つ（下表）
└── photos     : 別テーブル（1 投稿に 0〜n 枚）

report_comments（コメント）
└── 一般コメントと行政コメントを is_official で区別する
```

| category | details に入るもの |
|---|---|
| `hazard`（老朽化・危険箇所） | `hazardType`（道路／照明／護岸／公園遊具／その他） |
| `flood`（浸水） | `rainfallMm`（投稿時の 1 時間降水量）・`observedAt`・`amedasStation`・`depthLevel`（足首／膝／腰） |
| `spot`（観光おすすめ） | `spotType`（景観／お土産／飲食／その他） |

- `details` は**表示にしか使わない**（絞り込みは `category` と `city_code` で足りる）。
  だから JSON で持ってよい。検索条件に使いたくなった時点で、その項目だけ列に昇格させる
- **カテゴリを増やす作業＝ `category` の値と `details` の型を 1 つ足すだけ**にする。
  これが後半のフェーズ（F-6）を安く済ませる仕掛けになっている

### 統一しない部分

**地図上の見せ方だけはカテゴリごとに変える**（色・アイコン・既定の表示 ON/OFF）。
防災の投稿と観光の投稿が同じ見た目で混ざると、地図が読めなくなるため。
定義は既存の `app/src/lib/layers.ts` と同じ形式に揃える。

## 5. データモデル（論理）

物理スキーマ（型・インデックス・制約）は
[`interfaces.md`](interfaces.md) と `app/db/init/` の SQL が正本。ここには**何を持つか**だけ書く。

| テーブル | 役割 | 主なカラム |
|---|---|---|
| `municipalities` | **市町村マスタ**。千葉県全域対応の要 | `code`（5 桁）, `name`, `center_lat`, `center_lon`, `zoom`, `bbox` |
| `users` | ログインしたユーザー | `id`, `provider`, `provider_uid`, `display_name`, `role`（`user` / `gov`）, `gov_city_code` |
| `reports` | **投稿**（危険箇所・浸水・観光おすすめの共通モデル） | `id`, `category`, `title`, `body`, `lat`, `lon`, `city_code`, `user_id`, `status`, `details`(JSON), `created_at` |
| `report_photos` | 投稿に付く写真 | `id`, `report_id`, `file_name`, `mime_type`, `byte_size`, `sort_order` |
| `report_comments` | 投稿へのコメント | `id`, `report_id`, `user_id`, `body`, `is_official`, `created_at` |

- **`status`**（行政の対応状況）: `open`（受付前）／`ack`（受付）／`in_progress`（対応中）／`done`（対応済）。
  更新できるのは行政ユーザーだけ
- **`role = 'gov'` は `gov_city_code` を必ず持つ**。市川市の職員が船橋市の投稿の
  対応状況を変えられてはいけないので、**自分の市町村の投稿にだけ**行政操作を許す
- **位置は `lat` / `lon` の数値カラム**で持ち、両方にインデックスを張る。
  PostGIS は使わない（理由は [§7](#7-外部サービスとデータ) の設計判断）

## 6. 画面一覧

**画面は増やさない。** 1 枚の地図の上でモードを切り替える作りにして、
実装量と「動かない画面」のリスクを抑える。

| # | 画面 | パス | 中身 | ログイン |
|:-:|---|---|---|:---:|
| S-1 | 地図（防災モード） | `/` | ハザードマップ・避難場所・AED・危険箇所投稿・浸水投稿・注意案内 | 不要 |
| S-2 | 地図（観光モード） | `/?mode=tourism` | 景観スポット・観光おすすめ投稿・周遊ルート | 不要 |
| S-3 | 投稿の詳細パネル | S-1 / S-2 内のサイドパネル | 写真・本文・雨量などの固有項目・コメント欄・対応状況 | 閲覧は不要 |
| S-4 | 投稿フォーム | S-1 / S-2 内のモーダル | 位置・写真・本文・カテゴリ固有項目 | **必要** |
| S-5 | 投稿一覧 | `/reports` | 新着順のリスト。市町村・カテゴリで絞り込み。地図に飛べる | 不要 |
| S-6 | ログイン | `/login` | Google ログイン、またはデモログイン | — |
| S-7 | 出典・このサイトについて | `/about` | 使っているオープンデータと外部サービスのクレジット（**既存画面を拡張**） | 不要 |

- S-1 と S-2 は**同じ地図コンポーネント**で、有効なレイヤーの組が違うだけ
- 市町村の切り替えは全画面共通のセレクタで行い、`city` クエリで持ち回る（[§7](#7-外部サービスとデータ)）
- モバイル幅ではサイドパネルをボトムシートにする。**現地から投稿する使い方が本命**なので、
  投稿フォームまでの導線はスマホ幅で最短になるようにする

## 7. 外部サービスとデータ

**認証キーが要る外部サービスは使わない**（Google OAuth だけが例外で、
未設定時はデモログインに落ちる）。審査員が `docker compose up` だけで
動かせることを最優先にしている。

### 7-1. 使う外部サービス

| 用途 | サービス | キー | 出典表記 |
|---|---|:---:|---|
| 背景地図 | 国土地理院「淡色地図」タイル | 不要 | 既存（`app/src/lib/credits.ts`） |
| **ハザードマップ（F-1）** | **国土地理院ハザードマップポータル「重ねるハザードマップ」タイル** | **不要** | 追加する |
| 徒歩経路 | OSRM（FOSSGIS e.V.） | 不要 | 既存 |
| **雨量・雨予報（F-3・F-4）** | **気象庁の防災情報 JSON**（アメダス実況・府県予報） | **不要** | 追加する |
| ログイン（F-8） | Google OAuth | **要**（未設定時はデモログイン） | — |

**ハザードタイルの疎通は実測で確認済み**（2026-08-24・市川市 z=14 のタイルで確認）。

| 種別 | タイル | 市川市 |
|---|---|:---:|
| 洪水浸水想定区域（想定最大規模） | `01_flood_l2_shinsuishin_data` | 200 |
| 高潮浸水想定区域 | `03_hightide_l2_shinsuishin_data` | 200 |
| 津波浸水想定 | `04_tsunami_newlegend_data` | 200 |
| 土砂災害警戒区域 | `05_dosekiryukeikaikuiki` | **404**（市川市は平地で該当区域が無い） |

**F-1 で出すのは洪水・高潮・津波の 3 種**。土砂災害は市川市に該当が無いので
デモに載せず、千葉県内の該当市町村へ広げるときに追加を検討する。
**タイルが無い＝安全ではない**ので、凡例には「この地域には該当する想定区域の
データがありません」と明示し、白紙を「危険なし」と誤読させない。

### 7-2. 使うオープンデータ

既存の 3 レイヤーに加えて、観光用の 1 本を追加する。

| データ | 件数 | 用途 | 状態 |
|---|---:|---|---|
| 指定緊急避難場所（市川市） | 123 | 防災モード | 取得済・GeoJSON 化済 |
| AED 設置箇所（市川市） | 304 | 防災モード | 取得済・GeoJSON 化済 |
| 子育て施設（市川市） | 388 | 防災モード | 取得済・GeoJSON 化済 |
| **いちかわ景観100選** | **100** | **観光モード（F-5 の主データ）** | **要取得・要 GeoJSON 化** |
| 文化財一覧（市川市） | 79 | 観光モードの補助 | 要取得（解説文が全件空なので点の追加のみ） |

- 景観100選は 100 件すべてに座標・日本語解説・英語解説・カテゴリ（まち並み／自然／歴史・文化／生活風景）がある
- 変換は既存の `data/scripts/build_geojson.py` に**関数を 1 つ足す**形で行う。
  出力先も既存と同じ `app/public/data/`

### 7-3. 設計判断: PostGIS を使わず、緯度経度の数値カラムで持つ

| 選択肢 | 判断 |
|---|---|
| `postgres:17-alpine`（Docker 公式イメージ）+ 緯度経度カラム | **採用** |
| `postgis/postgis` イメージ | 不採用 |

理由は 3 つ。**①** 提出要件が「ベースイメージは可能な限り Docker 公式イメージ（DOI）」と
定めており、`postgis/postgis` は DOI ではない。**②** 必要な地理演算は
「地図の表示範囲に入る投稿を引く」（矩形の範囲検索）と「2 点間の距離」だけで、
どちらも数値カラムと Haversine 式で足りる。**③** 投稿は 1 市あたり多くて数百件の規模で、
インデックス無しでも問題にならない量。

PostGIS が要るのは「ポリゴンとの交差判定」を DB でやりたくなったときだが、
ハザードマップは**タイル画像として重ねるだけ**でポリゴンを DB に入れないので、その必要が無い。

### 7-4. 設計判断: 千葉県全域対応の建付け

**市川市をハードコードしない。** 全域対応の骨格だけ先に作り、データを市川市だけ入れる。

- 市町村は **JIS X 0402 の 5 桁コード**で識別する（市川市 = `12203`）
- `municipalities` テーブルに市町村マスタを持ち、**地図の初期表示位置・ズーム・範囲**を
  そこから引く。コード内に座標を直接書かない
- 投稿・レイヤー・注意案内はすべて `city_code` で絞る
- URL は `?city=12203` で持ち回り、**未指定なら市川市**（デモの既定値）
- 千葉県内の他市町村を足す作業は「**マスタに 1 行足す + そのデータを GeoJSON 化する**」だけになる。
  この「増やし方」がプレゼンで語る拡張性の実体

## 8. 認証

### 8-1. 二段構えにする理由

要件は「**Google アカウントでログイン**」だが、そのまま作ると提出要件と正面衝突する。

| 提出要件 | Google OAuth をそのまま入れた場合 |
|---|---|
| 審査員が `docker compose up` **だけ**で動かせること | クライアント ID / シークレットが無いとログインできず、**投稿機能が 1 つも試せない** |
| 認証キーが必須の外部サービスを使わない | Google の OAuth クライアントは必須キーそのもの |
| public リポジトリにシークレットを置かない | `.env` を配ることもリポジトリに入れることもできない |

コード評価は「実装割合 × **正しく動作する割合**」なので、
**審査員の環境で投稿機能が動かない構成は、実装した分がまるごと死ぬ**。

そこで **Google OAuth を本線としつつ、キーが未設定の環境では自動でデモログインに落ちる**
二段構えにする。これは審査対策であると同時に、
**開発者が誰でもキー無しで開発できる**という実用上の利点もある。

### 8-2. 動作

```
起動時に GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET を確認
├── 両方セットされている → Google モード
│     /login に「Google でログイン」ボタン。OAuth で認証し、
│     users テーブルに provider='google' で登録する
└── どちらか欠けている  → デモモード（審査員の既定はこちら）
      /login に「デモログイン」フォーム。表示名を入れるだけで入れる。
      users テーブルに provider='demo' で登録する
      画面上部に「デモモードで動作中」と常時表示する
```

- **モードの判定はサーバー側で 1 回**行い、結果（`authMode`）を画面に渡す。
  クライアント側でキーの有無を判定しない
- セッションは **JWT**（DB セッションを持たない）。テーブルとコードが 1 つ減る
- **デモモードでも、投稿・写真アップロード・コメント・行政操作まで全機能が試せる**。
  ここを落とすと二段構えにした意味が無い。**これは要件**であって「できたらいい」ではない
- `readme.txt` の「3. ログイン情報」に、デモログインの手順を書く（提出要件の項目）

### 8-3. 行政ロールの付与

| 環境 | 付与方法 |
|---|---|
| **デモモード** | デモログイン画面で「**一般ユーザー**」「**行政ユーザー（市川市）**」を選べる。<br>審査員が行政側の機能（公式コメント・対応状況の更新）も試せるようにするため |
| **Google モード** | 環境変数 `GOV_ACCOUNTS`（`メールアドレス:市町村コード` のカンマ区切り）に<br>載っているアカウントでログインしたとき `role='gov'` を付ける |

- 実運用では自治体ごとの職員アカウント管理が要るが、**ハッカソンのスコープ外**。
  環境変数による付与で「仕組みとしては成立する」ことを示すに留める
- デモモードでロールを自己申告できるのは**デモモードだからこそ許される**。
  Google モードでは自己申告させない（環境変数でのみ付与）

### 8-4. シークレットの取り扱い

| ファイル | 中身 | Git |
|---|---|---|
| `app/.env.example` | キーの**名前と説明だけ**。値は空 | **コミットする** |
| `app/.env` | 実際の値 | **コミットしない**（`.gitignore` 済み） |
| `compose.yaml` | `env_file: .env`（ファイルが無くても起動する書き方にする） | コミットする |

**このリポジトリは public。** クライアントシークレットが 1 度でも履歴に入ると、
public リポジトリでは誰でも過去コミットから読める。コミット前に
`bash .github/scripts/secret_scan.sh` を実行する。

Next.js は `.env` だけでなく **`.env.local` / `.env.production.local` も既定で読む**ため、
開発者が `app/.env.local` を作る可能性が高い。`.env` だけを除外していても防げないので、
**`.gitignore` に `.env` `.env.local` `.env.*.local` の 3 つをまとめて入れてある**
（この要件定義と同じ PR で対応済み）。

### 8-5. 必要な環境変数

| 変数 | 必須 | 用途 | 未設定のとき |
|---|:---:|---|---|
| `DATABASE_URL` | ○ | PostgreSQL 接続先 | `compose.yaml` が既定値を渡す |
| `AUTH_SECRET` | △ | JWT の署名鍵 | デモ用の固定値を使い、**警告をログに出す** |
| `GOOGLE_CLIENT_ID` | — | Google OAuth | **デモモードに切り替わる** |
| `GOOGLE_CLIENT_SECRET` | — | Google OAuth | 同上 |
| `GOV_ACCOUNTS` | — | 行政ロールの付与 | 行政ユーザーは Google モードでは 0 人 |

## 9. 実装順序

**スコープは「全部作る」。この節が決めるのは削る量ではなく作る順番。**

### 9-1. 全フェーズ共通の完了条件

審査のコード評価が「実装割合 × **動作割合**」の掛け算である以上、
**作りかけを積み上げるのが最悪手**。どのフェーズも、終わった時点で次を全部満たす。

1. **`cd app && docker compose up` だけで起動する**（追加の手順・キー・手動投入が要らない）
2. **前のフェーズまでの機能が壊れていない**（地図が出る・点が出る・経路が引ける）
3. `npm run typecheck` が通る
4. `bash tools/package_submission.sh --smoke` が通る（提出できる状態が常に保たれている）
5. `bash .github/scripts/secret_scan.sh` が通る

**この 5 つが揃わないうちに次のフェーズへ進まない。**
途中で時間切れになっても、そこまでが「動く提出物」になっている状態を維持する。

### 9-2. 順番

| # | フェーズ | 入る機能 | 完了時に `docker compose up` で確認できること |
|:-:|---|---|---|
| **P0** | 済 | — | 地図・避難場所 123・AED 304・子育て施設 388・徒歩ナビ |
| **P1** | ハザードマップ | F-1 | 洪水／高潮／津波の想定区域を地図に重ねられる。凡例・不透明度・出典が出る |
| **P2** | DB と認証の基盤 | F-8（デモ側） | `db` コンテナが立ち、`web` が healthcheck を待って起動する。デモログインでログイン／ログアウトできる |
| **P3** | 投稿基盤 + 危険箇所報告 | F-2 | ログインして位置・写真・説明を投稿でき、地図にピンが出て、詳細パネルとコメントが動く |
| **P4** | 浸水報告 | F-3 | カテゴリ「浸水」で投稿でき、**投稿時点の雨量が自動で記録**されて詳細に出る |
| **P5** | 観光モード | F-5・F-6 | 景観100選 100 件が地図に出て解説が読め、徒歩ルートが引ける。観光おすすめ（お土産含む）を投稿できる |
| **P6** | 行政からの応答 | F-7 | 行政ユーザーで公式コメントを付け、対応状況を「対応中」「対応済」に変えられる |
| **P7** | 注意案内 | F-4 | 雨予報が出ている市町村で、過去に浸水報告のある地点に注意表示が出る |
| **P8** | Google ログイン | F-8（本線） | キーを設定した環境では Google ログインになり、**未設定なら P2 のデモログインのまま動く** |

### 9-3. なぜこの順番か

- **P1 を最初に置く**のは、DB も認証も要らず**既存の地図土台にタイルを 1 枚重ねるだけ**で
  機能が 1 つ完成するから。最も安い実装で「動く機能」を増やし、
  掛け算の分母（実装割合）と分子（動作割合）を同時に押し上げる
- **P2（DB 追加）を早い段階に置く**のは、ここが**構成を変える唯一の危険なフェーズ**だから。
  コンテナが 1 つから 2 つになり、`depends_on` と `healthcheck` の待ち合わせが入る。
  ここで詰まると全部が止まるので、**時間の余裕があるうちに通しておく**
- **P3 が本丸**。[§4](#4-設計判断-3-種類の投稿を-1-つのモデルに統一する) で投稿を 1 モデルに
  統一したので、**P3 さえ通れば P4・P5・P6 はカテゴリと表示の追加で済む**。
  投稿基盤に一番厚く時間を積む
- **P7（注意案内）を後ろに置く**のは、F-3 で投稿が溜まらないと何も表示できないから。
  順番を逆にすると「動くかどうか確かめられない機能」を先に書くことになる
- **P8 を最後に置く**のは、**審査員の環境では検証されない唯一の機能**だから。
  ここが未完成でもデモログインで全機能が動く（[§8-2](#8-2-動作)）ので、
  最も後回しにして安全な部分になっている

### 9-4. 締切から見た配分

コード提出は **2026-09-09（水）17:00**。個別相談が **9/3・9/4** にある。

- **9/3・9/4 の個別相談までに P3 まで**通しておく。
  相談で見せられるものが「地図だけ」か「投稿が動くところ」かで、もらえる助言の質が変わる
- **P7・P8 は 9/9 直前に触らない**。締切前日に構成へ手を入れて起動しなくなるのが
  最も高くつく失敗。最後の 1 日は `readme.txt`・説明資料 PDF 2 種・
  `tools/package_submission.sh` による最終検証に充てる

## 10. 論点（未決）

### 10-1. 投稿の悪用対策をどこまでやるか — **実装是非は未決**

CHIZUBA は**誰でも位置と写真を投稿できる**サービスなので、次のリスクを構造的に抱える。

| リスク | 起きること |
|---|---|
| スパム投稿 | 広告・無関係な投稿が地図を埋め、防災情報が読めなくなる |
| 不適切な画像 | 公序良俗に反する画像がアップロードされる |
| 虚偽の浸水報告 | **F-4 の注意案内の根拠が汚染される**。防災機能なので影響が大きい |
| 位置情報の巻き添え | 自宅前の危険箇所を報告した結果、投稿者の住所が推定される |

**実務であれば必須**だが、**このハッカソンで実装するかは決めていない**。判断材料を挙げておく。

- **やらない理由**: 対策そのものは審査 5 項目のどれにも直接効かない。
  一方でコストは高い（通報導線・非表示フラグ・行政の削除権限・監査ログ）。
  実装割合 × 動作割合の掛け算では、**同じ工数を F-1〜F-8 の完成度に使うほうが得**
- **やる理由**: 「住民投稿を防災に使う」という提案に対し、審査員から
  **「虚偽報告はどうするのか」という質問はほぼ確実に来る**。
  何も考えていないと「有効性と実現性」で落ちる
- **中間案**: **実装せず、設計として答えを用意しておく**。
  ログイン必須（＝投稿者が特定できる）・行政ユーザーによる対応状況の更新（＝行政の目が入る）・
  写真の形式とサイズの制限、という**既に入っている要素で一次防御は成立している**ことを説明し、
  本格的な対策は「運用フェーズの課題」として資料に明記する

**現時点の暫定方針は中間案。** ただし次の 2 つは**実装側で必ず入れる**（対策ではなく入力の健全性として）。

- アップロードできる画像の**形式（JPEG / PNG / WebP）とサイズ上限**を決めてサーバー側で弾く
- 1 投稿あたりの本文・タイトルの**文字数上限**をサーバー側で弾く

この節の結論はチームで決める。決まったらこの節を書き換える。
