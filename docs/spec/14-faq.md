**各回答には根拠のファイルパス（必要なら行番号）を付けた。**

答え方の型:

## A. 構成と技術選定（Q1〜Q10）

### Q1. 全体の構成を 30 秒で説明してください

**コンテナ 2 つです。** Next.js のサーバー（`web`）と PostgreSQL 17（`db`）で、
それ以外に動いているものはありません。
行政のオープンデータ（避難場所・AED・子育て施設・景観100選）は
**GeoJSON としてアプリに同梱**してあり DB を通らず、
**DB を使うのは住民と行政の投稿だけ**です。
背景地図・ハザード・徒歩経路・気象は外部サービスから取りますが、
**どれも認証キーが要りません**。

根拠: `app/compose.yaml`・[01 章](01-overview.md)

### Q2. なぜ Google マップを使わないのですか

**API キーと課金アカウントが必須で、審査員の環境で地図が出せなくなるからです。**
このアプリの主役は国土地理院のタイルと国土交通省のハザードタイルを**重ねること**なので、
任意の XYZ タイルをそのままレイヤーにできる MapLibre のほうが素直です。
MapLibre は BSD ライセンスのオープンソースなので、
規約変更で急に使えなくなる心配もありません。

根拠: `app/src/lib/basemap.ts`・`app/src/lib/hazards.ts`・[11 章 11-1](11-decisions.md#11-1-なぜ-maplibre-gl-js-かgoogle-maps-でも-mapbox-でもなく)

### Q3. PostGIS を使えばもっと簡単だったのでは

**必要な地理演算が「矩形の範囲検索」と「2 点間の距離」だけ**なので使いませんでした。
どちらも緯度経度の数値カラムと Haversine 式で足ります。
提出要件がベースイメージに Docker 公式イメージを求めていて、
**PostGIS のイメージは公式ではない**という理由もあります。
PostGIS が要るのはポリゴンとの交差判定を DB でやりたいときですが、
ハザードマップは**タイル画像として重ねるだけ**なのでその必要がありません。

根拠: `app/db/init/001_schema.sql:11`・`app/src/lib/geo.ts:haversineMeters`

### Q4. なぜ PostgreSQL で、SQLite ではないのですか

**3 つの機能が要ったからです。** ①`jsonb`（3 カテゴリを 1 テーブルに統一する設計の前提）、
②`normalize(text, NFKC)`（全角半角をそろえた検索。PostgreSQL 13 以降の**組み込み**で拡張不要）、
③`timestamptz` と `AT TIME ZONE`（JST の暦日で絞る処理）。
SQLite はこの 3 つがどれも弱く、また `docker compose` で
「コンテナ 2 つ」を見せるほうが提出要件の例に沿います。

根拠: [11 章 11-3](11-decisions.md#11-3-なぜ-postgresql-17-か)・[PostgreSQL 17 の文字列関数](https://www.postgresql.org/docs/17/functions-string.html)

### Q5. データベースの設計を説明してください

**テーブルは 5 つです。**
`reports`（投稿・3 カテゴリ共通）、`report_photos`（写真のファイル名）、
`report_comments`（コメント）、`users`（ログインした人）、
`municipalities`（市町村マスタ）。
これに加えて `app_instance` という**1 行だけのテーブル**があり、
セッションをこの DB に縛るための UUID を持っています。
索引は 6 本で、一覧の WHERE 句と ORDER BY に合わせてあります。

根拠: `app/db/init/001_schema.sql`（138 行）・[05 章](05-database.md)

### Q6. なぜ投稿を 1 つのテーブルにまとめたのですか

**利用者から見れば「位置＋写真＋説明を投稿する」という同じ操作だから**です。
分けるとテーブル 3・API 3 本 ×5 メソッド・フォーム 3・地図レイヤー 3 組になり、
カテゴリを増やすたびに全部が増えます。
統一した結果、**カテゴリを増やす作業は `REPORT_CATEGORIES` に 1 行足すだけ**になり、
`ReportForm.tsx`（345 行）には**カテゴリ固有のコードが 1 行もありません**。
違いは `category` 列と `details`（jsonb）だけで吸収しています。

根拠: `app/src/lib/reports.ts:46-107`・`app/src/components/ReportForm.tsx`

### Q7. なぜ静的な GeoJSON を DB に入れないのですか

**更新頻度が違うから**です。避難場所や AED は年 1 回程度しか変わらない一方、
投稿は毎日増えます。同じ場所に置くと、データを更新するのに
`docker compose down -v` が必要になってしまいます。
GeoJSON なら **ブラウザが直接読んで MapLibre のソースにできる**ので、
サーバーも DB も経由しません。

根拠: `app/src/lib/layers.ts`・`app/src/components/MapExplorer.tsx` の `useEffect`

### Q8. なぜ Next.js なのですか

**地図の UI とサーバー側の中継 API を 1 コンテナに収められるから**です。
気象庁と OSRM はブラウザから直接叩けない（User-Agent の明示・キャッシュ・
1 秒 1 リクエストの制限が要る）ので、サーバー側の受け口が必要でした。
Next.js なら同じプロジェクトの `app/api/**/route.ts` がそれになります。
`output: "standalone"` で実行イメージを小さくできるのも決め手です。

根拠: `app/next.config.ts:6`・`app/src/app/api/`

### Q9. なぜこの Docker 構成なのですか

**3 ステージに分けて、実行イメージに開発用の依存とソースを入れないため**です。
`deps` で `npm ci`、`builder` で `npm run build`、`runner` は
`.next/standalone` と `public` だけをコピーします。
タグは `node:22-slim` / `postgres:17-alpine` と**固定**（`latest` を使わない）、
`depends_on` の `service_healthy` で DB の起動を待ちます。

根拠: `app/Dockerfile`・`app/compose.yaml:61-65`

### Q10. どこまで自分たちで作ったのですか

**アプリのコードはすべて自分たちで書きました。**
使っている外部の部品はライブラリ（Next.js・React・MapLibre・Auth.js・pg・Tailwind・
lucide-react）とデータ（オープンデータ・地図タイル・気象 JSON・OSRM）で、
**アプリのロジックを提供する既製品は使っていません**。
生成 AI を実装に使いましたが、**中身は把握していて説明できます**（この仕様書がその証拠です）。

根拠: `app/package.json`（依存 9 個）・`docs/spec/`

## B. データと権利（Q11〜Q17）

### Q11. オープンデータの出典はどう扱っていますか

**`app/src/lib/credits.ts` を正本にして、地図の隅と `/about` の 2 か所に出しています。**
市川市データは CC BY 4.0、千葉県データは PDL1.0（公共データ利用規約）で、
どちらも**出典を書けば二次利用できる**ライセンスです。
加工した場合は「加工して作成」も併記しています。
GeoJSON の中にも `attribution` を埋め込んであるので、
データだけ取り出しても出典が付いてきます。

根拠: `app/src/lib/credits.ts` の `DATA_CREDITS`（6 件）・`data/*/SOURCE.md`

### Q12. 写真の権利はどうしていますか

**再利用が許されたものだけ**（CC0・パブリックドメイン・CC BY・CC BY-SA）です。
NC（非営利限定）・ND（改変禁止）・ライセンス不明は 1 枚も使っていません。
CC BY と CC BY-SA は作者の表示が条件なので、**ポップアップと `/about` の両方に
作者名とライセンスを出し、コモンズの説明ページへリンク**しています。
加工したのは長辺 1000px への縮小と JPEG 再圧縮だけです。

根拠: `app/src/lib/scenicPhotos.ts`（54 枚）・`app/src/lib/credits.ts` の `DEMO_PHOTO_CREDITS`（17 枚）・`data/wikimedia-commons/SOURCE.md`

### Q13. デモ投稿の写真は市川市で撮られたものですか

**観光の 10 枚は市川市内ですが、防災の 7 枚は市外の参考写真です。**
市川市で実際に起きた被害の写真ではありません。
2026 年 8 月の千葉豪雨をはじめ、実際の災害の記録として使ってはいけないと
`data/wikimedia-commons/SOURCE.md` と `/about` に明記しています。

根拠: `data/wikimedia-commons/SOURCE.md`「写真と実際の場所の関係（**重要**）」

### Q14. 投稿された雨量は、本当にその場所の値ですか

**違います。最寄りのアメダスの値です。**
市川市にはアメダスが無く、**最寄りの船橋まで 10.2 km** あります
（2026-09-03 に気象庁の `amedastable.json` を取得して計算した実測値）。
局地的な豪雨は数 km で降り方が変わるので、
画面には**必ず観測所名と距離を添えて**「船橋アメダス（約 10.2 km）」と出します。
20 km 以上離れていれば雨量そのものを出しません。

根拠: `app/src/lib/weather.ts:formatStation`・`AMEDAS_MAX_DISTANCE_KM = 20`

### Q15. F-4 の注意案内は「予測」ではないのですか

**予測ではありません。事実 2 つを並べているだけ**です。
「過去にこの地域で浸水の報告が N 件あります」と
「気象庁の予報では今後 24 時間の降水確率が最大 X% です」。
独自のモデルも推定も持っていません。
**気象業務法第 17 条第 1 項**が気象庁以外の予報業務を許可制にしているので、
「浸水するでしょう」に類する表現はコードにも画面にも入れていません。

根拠: `app/src/components/FloodAlertCard.tsx` の冒頭コメント・
[e-Gov 法令検索の気象業務法](https://laws.e-gov.go.jp/law/327AC0000000165)（2026-09-03 に条文を取得して確認）

### Q16. 個人情報はどう扱っていますか

**画面に出るのは表示名だけ**です。メールアドレスと `provider_uid` は
API のレスポンスにも書き出しにも含めません（`session` コールバックで
`email: ""` に潰しています）。
ただし**正直に言うと 3 つ弱点があります**: ①暗号化セッション Cookie の中には
Google のメールと画像 URL が残る、②写真は受け取ったバイト列をそのまま保存するので
**Exif が消えない**、③アカウントを利用者自身で消す画面が無い。
これは `/privacy` にそのまま書いてあります。

根拠: `app/src/lib/auth.ts:226-228`・`app/src/app/privacy/page.tsx`・`app/src/lib/photoStore.ts`

### Q17. 「千葉県全域」と言いますが、データは市川市だけでは

**デモデータは市川市だけですが、建付けは全域対応です。**
市町村ごとの座標・ズーム・範囲は**コードに書かず `municipalities` テーブルに置いて**あり、
**市町村を増やす作業は 1 行の INSERT だけ**でコードの変更は要りません。
気象の予報区も `area.json` の親子をたどるので全国分に効きます。
制約は「地図に載せる GeoJSON をその市の分だけ用意する必要がある」ことです。

根拠: `app/db/init/002_seed_municipalities.sql:6-7`・`app/src/lib/jma.ts:resolveForecastArea`

## C. 認証・セキュリティ（Q18〜Q26）

### Q18. デモモードだと誰でも行政ロールを名乗れるのでは

**手元で動かすぶんはそのとおりで、それは意図した設計です**
（審査員が `docker compose up` だけで行政側の機能を試せるようにするため）。
**インターネットに公開するときは `GOV_DEMO_PIN` を設定**すると、
行政ロールを選ぶときだけ PIN を要求します。
一般ユーザーのログインには一切影響しません。
総当たり対策は指数バックオフ（最大 8 秒）と連続 10 回で 60 秒のロックで、
6 桁なら 10⁶ ÷ 10 × 60 秒 ≒ **69 日**かかる計算です。

根拠: `app/src/lib/govPin.ts:44-61`

### Q19. 権限のチェックはどこでやっていますか

**必ず API 側でセッションを見て判定します。画面の `role` は表示の出し分けにしか
使いません。** `PATCH /api/reports/:id` は 1 本の経路に 2 つの操作が載っているので、
**含まれている項目ごとに権限を確かめます**:
`status` なら「担当市町村の行政ユーザーか」、
`title`/`body`/`details` なら「投稿者本人か」。
**行政ユーザーでも他人の本文は書き換えられません。**

根拠: `app/src/app/api/reports/[id]/route.ts:79-89`・[06 章 6-7](06-auth.md#6-7-api-ごとの認可チェック一覧表)

### Q20. 市川市の職員が船橋市の投稿を操作できませんか

**できません。** `users.gov_city_code`（担当市町村）と `reports.city_code` が
一致するときだけ通します。対応状況の更新も公式コメントも同じ条件です。
`city_code` は**クライアントから受け取らず**、サーバーが投稿の座標を
市町村マスタの bbox と突き合わせて決めるので、詐称もできません。

根拠: `app/src/app/api/reports/[id]/route.ts:79`・`comments/route.ts:46-47`・`reportStore.ts:resolveCityCode`

### Q21. セッションはどう管理していますか

**JWT で、DB セッションは持ちません。** 中身は `uid`・表示名・ロール・
担当市町村と、**このインストールの ID（`inst`）**です。
`users.id` はただの連番なので、これが無いと**別の場所で動いている CHIZUBA の
トークンを見分けられません**。実際に、別 DB で発行した行政トークンを
持ち込んだら行政操作が通ってしまった（`uid = 9` はその DB に存在すらしなかった）ので、
DB の `app_instance.install_id` から**署名鍵を導き、トークンにも焼き込んで
毎回突き合わせる**二重の縛りにしました。

根拠: `app/src/lib/installId.ts` の冒頭コメント・`app/src/lib/auth.ts:181-185`

### Q22. `AUTH_SECRET` を設定しなくても安全ですか

**はい。未設定なら `sha256("chizuba-session-key:" + install_id)` を使う**ので、
環境ごとに違う鍵になります。`install_id` は
`gen_random_uuid()` で作られる UUID で、DB の中にしかありません。
以前は公開の固定値を書いていて、リポジトリを読めば誰でもトークンを偽造できました。
それを直したのがこの仕組みです。

根拠: `app/src/lib/auth.ts:65-80`・`app/db/init/001_schema.sql:28-33`

### Q23. 画像でないファイルを画像として上げられませんか

**できません。申告された MIME タイプを信じず、先頭バイトも確かめます。**
JPEG は `FF D8 FF`、PNG は 8 バイトのシグネチャ、WebP は `RIFF….WEBP` を見ます。
申告と中身が食い違うときは**中身のほうを正**として記録します。
サイズは 1 枚 5 MB・1 投稿 3 枚・1 リクエスト 10 MB まで。
ファイル名は UUID で作り直すので、投稿された名前は使いません。

根拠: `app/src/lib/photoStore.ts:sniffImageType`・`app/src/lib/reportInput.ts:parsePhotos`

### Q24. SQL インジェクションや XSS の対策は

**SQL は全部プレースホルダ（`$1`, `$2`…）で、文字列連結で組む箇所はありません。**
XSS は React が既定でエスケープします。地図のポップアップだけは素の DOM を組み立てますが、
**`textContent` で入れている**（`innerHTML` を使わない）ので、
オープンデータの中の記号が markup として解釈されることはありません。
CSV の書き出しでは、利用者が書いた文字列が `=` `+` `-` `@` で始まるときに
先頭に `'` を足して、表計算ソフトが数式として実行するのを止めています。

根拠: `app/src/lib/reportStore.ts` の各 SQL・`MapView.tsx:popupRow`・`reportExport.ts:csvText`

### Q25. 荒らしや大量投稿への対策はありますか

**レート制限は入れていません。** ログインを必須にし、
入力の上限（タイトル 60 字・本文 1000 字・写真 3 枚 5 MB）を設けているだけです。
実運用なら投稿頻度の制限と通報・非表示の仕組みが要ります。
**そこは未実装で、技術的負債として認識しています。**
現状で守っているのは「行政を騙れないこと」（`isOfficial` はサーバーが決める）です。

根拠: [13 章 13-6](13-limitations.md#13-6-セキュリティ上の割り切り)

### Q26. `X-Forwarded-Host` を偽装されませんか

**偽装はできますが、実害は「偽装した本人が別の住所へ飛ぶ」ことだけ**です。
他人のセッションは取れません。これは Auth.js の `trustHost: true` の
既定の割り切りに合わせています。
ヘッダーの形は正規表現で検査していて（改行や `/` が混ざったものは弾く）、
弾いたあとは `Host` に落ちます。
固定したい運用では `AUTH_URL` を設定すればそちらが優先されます。

根拠: `app/src/lib/publicOrigin.ts:40-56`

## D. 性能・規模（Q27〜Q31）

### Q27. 同時アクセスは何人まで耐えられますか

**測っていません。負荷試験をしていないので、正直に「未測定」です。**
分かっているのは、DB の接続プールが**最大 10**、
Node.js は単一プロセス、web コンテナは 1 個ということだけです。
キャッシュが効くので気象庁への問い合わせは 10 分に 1 回に抑えられ、
OSRM は 1 秒 1 リクエストで直列化されます（**ここが最も詰まりやすい**）。
実運用なら web を複数立てて `AUTH_SECRET` を共有する形になります。

根拠: `app/src/lib/db.ts:40`・`app/src/app/api/routing/route.ts:24`・[13 章 13-4](13-limitations.md#13-4-性能規模の制約未測定のものは未測定と書く)

### Q28. 投稿が何万件になったらどうなりますか

**一覧は 500 件（書き出しは 1000 件）で打ち切るので、表示は破綻しません。**
問題になるのは**キーワード検索**で、
`lower(normalize(title, NFKC)) LIKE '%…%'` は前方一致でなく関数も通すので、
既存の B-tree 索引が効きません。式インデックスも `pg_trgm` も入れていないので、
数万件規模では遅くなります。
矩形検索（`lat`/`lon`/`city_code`/`category`）には索引が効きます。

根拠: `app/src/lib/reportStore.ts:whereFor`・`app/db/init/001_schema.sql:105-109`

### Q29. テストは書きましたか

**単体テストは 0 本です。テストフレームワークも入っていません。**
開発期間が約 1 か月で、採点が「実装した割合 × 正しく動作する割合」の掛け算なので、
**テストコードを書く時間を、実際に `docker compose up` して手で動かす検証に充てました**。
代わりに 4 本の機械的なゲート（型検査・ビルド・秘匿情報スキャン・提出物検証）を置いています。
リファクタのときは**レンダリング後の DOM を before/after で丸ごと突き合わせて**
差分ゼロを確認しました。**自動テストが無いことは技術的負債として認識しています。**

根拠: `app/package.json` に `test` スクリプトが無い・[12 章](12-quality.md)

### Q30. 画像は何 MB まで上げられますか

**1 枚 5 MB（正確には 5,242,880 バイト）、1 投稿 3 枚まで、
1 リクエスト全体で 10 MB まで**です。
形式は JPEG・PNG・WebP。DB の CHECK 制約（`byte_size <= 5242880`）と
コードの定数（`PHOTO_MAX_BYTES = 5 * 1024 * 1024`）を同じ値にしてあります。
リサイズはしていないので、5 MB の写真は 5 MB のまま保存・配信されます
（配信には 1 日のキャッシュが効きます）。

根拠: `app/src/lib/reports.ts:154-158`・`app/db/init/001_schema.sql:119`

### Q31. 投稿の位置精度はどのくらいですか

**利用者が地図をクリックした位置がそのまま座標になります。**
`double precision`（倍精度浮動小数点）で保存し、
**書き出しのときだけ小数 6 桁に丸めます**（RFC 7946 が「必要以上の桁を持たせない」ことを
勧めているため。小数 6 桁は約 0.1 m の分解能）。
現在地から自動で取る経路は無く、**必ず地図で指定します**（GPS の誤差を持ち込まないため）。
画面には投稿する場所を小数 5 桁で表示します。

根拠: `app/src/lib/reportExport.ts:round6`・`app/src/components/ReportForm.tsx` の座標表示

## E. 運用と実用性（Q32〜Q38）

### Q32. オフラインでも使えますか

**部分的に使えます。** 同梱の GeoJSON（避難場所 123・AED 304・子育て施設 388・
景観100選 100）は `app/public/` にあるのでインターネット無しでも点が出ます。
出ないのは背景地図のタイル・ハザードの重ね・徒歩経路・雨量です。
背景が出ない場合でも下地色（`#eeece5`）のレイヤーを敷いてあるので、
**点と経路は読めます**。

根拠: `app/src/lib/basemap.ts` の `background` レイヤー

### Q33. データの更新頻度はどうなっていますか

**3 段階あります。**
①**オープンデータ**（避難場所・AED など）は年 1 回程度の更新で、
`data/scripts/build_geojson.py` を実行して GeoJSON を作り直します（現在は令和 8 年 4 月 1 日版）。
②**気象**はサーバー側のキャッシュで、実況 10 分・予報 30 分・観測所一覧 24 時間。
③**投稿**はリアルタイム（キャッシュしません。`dynamic = "force-dynamic"`）。

根拠: `app/src/lib/jma.ts:42-48`・`data/ichikawa-city/SOURCE.md`

### Q34. 既存のハザードマップポータルと何が違うのですか

**ハザードマップは「行政が公表した想定」だけですが、CHIZUBA は
その上に「住民が今報告した実績」を重ねます。**
想定区域の外でも実際に冠水する場所はあり、それは住民しか知りません。
さらに**溜まった浸水報告に雨の予報を掛け合わせて注意を出す**（F-4）ので、
過去の実績が次の雨のときに役立ちます。
逆に、ハザードマップポータルのタイルをそのまま使わせてもらっているので、
**想定の部分では張り合っていません**。

根拠: `app/src/lib/hazards.ts`（タイルをそのまま重ねている）・`app/src/lib/weather.ts` の `buildFloodAlert`（実績 × 予報）・[04 章 4-4](04-features.md#4-4-f-4-注意案内)

### Q35. 市民報告型のサービスは既にありますが、違いは何ですか

**双方向であることと、投稿を持ち出せることです。**
行政が公式コメントを返し、対応状況を 4 段階で更新できるので、
「投稿したきり」になりません。
そして**住民が寄せた情報を CSV / GeoJSON で誰でも書き出せます**。
「行政が公開したデータを住民が使う」一方通行ではなく、
**住民が寄せた情報もオープンデータとして持ち出せる**のが CHIZUBA の建付けです。
加えて、防災と観光を 1 つの地図に載せている点も違います。

根拠: `app/src/app/api/reports/export/route.ts` の冒頭コメント

### Q36. 行政が本当に運用できますか

**必要な操作は 2 つだけ**にしてあります。投稿にコメントを書くことと、
対応状況を 4 段階（未対応／受付／対応中／対応済）で選ぶことです。
4 段階には**1 行の説明**を付けて、使い分けで迷わないようにしました。
アカウントは環境変数（`GOV_ACCOUNTS`）に
`メールアドレス:市町村コード` を書くだけで付与できます。
**実運用には自治体ごとの職員アカウント管理が要りますが、そこはスコープ外**で、
「仕組みとしては成立する」ことを示すに留めています。

根拠: `app/src/lib/reports.ts:122-127`・`app/src/lib/authMode.ts:47-48`

### Q37. 災害のときに本当に動きますか

**外部サービスが落ちても止まらないように作ってあります。**
気象庁が落ちても浸水報告は投稿でき（雨量が空欄になるだけ）、
OSRM が落ちても直線距離の概算に切り替わり、
**DB が落ちても地図・ハザード・オープンデータの点は出ます**。
ただし正直に言うと、**負荷試験をしていない**ので
「同時に何人まで」は答えられません。
また、この試作は自宅の Mac 1 台で公開しているだけで、冗長構成ではありません。

根拠: [08 章 8-6](08-external-apis.md#8-6-外部サービスが全部落ちたらどうなるか)

### Q38. 審査員が試すのに何が必要ですか

**Docker だけです。** `cd app && docker compose up` で
`http://localhost:3000` が開きます。
アカウント登録も API キーの取得も要りません。
**デモログインで表示名を入れるだけで、投稿・コメント・行政操作まで全機能が試せます。**
起動直後からデモ投稿 22 件・写真 17 枚・コメント 6 件が入っているので、
空の地図を見せることもありません。
3000 番が塞がっていれば `CHIZUBA_PORT=3100 docker compose up`。

根拠: `app/README.md`「動かす」・`app/db/init/003_seed_demo_reports.sql`

## F. 実装の詳細（Q39〜Q42）

### Q39. 実装で一番苦労したところはどこですか

**3 つあります。**
①**MapLibre v6 の Web Worker**。バンドルすると worker が自分の場所を見つけられず、
「背景地図は出るのに GeoJSON が永久に読み込み中」になる。エラーも出ないので原因が分からない。
②**ログインのリダイレクトが常に 3000 番へ飛ぶ**問題。`AUTH_URL` を外すだけでは直らず、
`output: "standalone"` が待ち受けアドレスから URL を組むところまで追う必要があった。
③**`date AT TIME ZONE 'Asia/Tokyo'` が逆向きに解決される**問題。
境目が 9 時間ずれて単日の指定が 1 件も引けなくなり、`::timestamp` の明示で解決しました。

根拠: `app/scripts/copy-maplibre-worker.mjs`・`app/src/lib/publicOrigin.ts`・`app/src/lib/reportStore.ts` の日付の SQL

### Q40. 生成 AI をどう使いましたか

**実装に使いました。ただし内容は理解していて説明できます。**
主催者が「生成 AI の利用は可、ただし内容を理解して説明できる状態にする」と
明言しているので、その条件を満たすために
**`docs/spec/`（この仕様書・全 16 ファイル）と `docs/manual/`（利用説明書）を
コードから起こして**あります。
設計判断の経緯は PR 本文（#3〜#33）と `.agent/progress.md` に残していて、
「何を試して何をやめたか」まで辿れます。

根拠: `docs/spec/`・`.agent/progress.md`

### Q41. コードの規模はどのくらいですか

**`app/src` が 11,240 行**（TypeScript / TSX / CSS / SVG）です。
内訳は `components/` **4,454 行**、`lib/` **4,700 行**、
`app/`（画面 5・API 8・CSS・アイコン）と `types/` で **2,070 行**。
これに SQL **371 行**、Python **2,298 行**（データ加工・分析・QR 生成・評価）、
シェルスクリプト **1,317 行**（提出物検証・秘匿情報スキャン・セルフホスト）が加わります。
**依存は 9 個**（Next.js・React・React DOM・MapLibre・Auth.js・pg・
Tailwind・`@tailwindcss/postcss`・lucide-react）。

根拠: `wc -l` の実測（2026-09-03）・`app/package.json:13-23`

### Q42. これからどう発展させますか

**3 つの段階を考えています。**
①**市町村を増やす**（`municipalities` に 1 行足すだけなので、
その市の GeoJSON を用意すれば動く）。
②**行政側の運用に足りないもの**を入れる（新着の通知・投稿の通報とモデレーション・
職員アカウントの管理）。
③**技術的負債の返済**（自動テスト・検索の索引・写真のリサイズ）。
順番は②が先で、①は「使われる自治体が決まってから」だと考えています。

根拠: [13 章](13-limitations.md)
