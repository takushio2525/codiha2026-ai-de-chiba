# 11. 設計判断とその理由

**「なぜそうしたのか」を聞かれたときの答え。**
根拠は `.agent/architecture.md`「設計判断の記録」・PR 本文・git log・実測から引いた。

---

## 11-0. 全体を貫く 1 つの原則

> **審査員が `docker compose up` だけで全機能を試せること。**

ここから他のほとんどの判断が導かれる。

- 認証キーが要る外部サービスを使わない（→ 11-1・11-2）
- 鍵が未設定でもログイン・投稿ができる（→ 11-7）
- DB のスキーマとデモデータが初回起動で自動的に入る（→ 11-3）
- 外部サービスが落ちても画面が止まらない（→ [08 章 8-6](08-external-apis.md#8-6-外部サービスが全部落ちたらどうなるか)）

コード評価が **「実装した割合 × 正しく動作する割合」の掛け算**である以上、
**動かない機能を積むより、動く機能を確実に仕上げる**（`AGENTS.md`）。

## 11-1. なぜ MapLibre GL JS か（Google Maps でも Mapbox でもなく）

| 候補 | 認証キー | 判断 |
|---|---|---|
| **MapLibre GL JS** | **不要** | **採用** |
| Google Maps JavaScript API | 必要（課金アカウントも） | 不採用 |
| Mapbox GL JS | 必要（アクセストークン） | 不採用 |
| Leaflet | 不要 | 検討したが不採用 |

**決め手は認証キー。** 審査員が鍵を用意しないと地図が出ないのは、
「`docker compose up` だけで動く」に反する。

MapLibre は Mapbox GL JS v1 から派生したオープンソースで、
**ベクトルタイルもラスタタイルも扱え、GeoJSON をソースとして直接読める**。
CHIZUBA は「ラスタ 2 種類（背景・ハザード）＋ GeoJSON 5 本」を重ねるので、
この組み合わせが素直に書ける。

Leaflet でも同じことはできるが、**MapLibre の「式（expression）」で
色分けと表示切り替えを宣言的に書ける**のが大きい。
点が 900 個以上あっても、JavaScript でループを回さずに済む（[07 章 7-2](07-map.md#7-2-レイヤーの積み順)）。

**代償**: v6 の Web Worker が自分の場所を見つけられない罠がある
（[07 章 7-3](07-map.md#7-3-worker-の罠)）。これは対処済み。

## 11-2. なぜ背景地図が国土地理院か

- **認証キー不要**。出典を明記すれば自由に利用できる
- **国内で安定**していて、日本の地名・道路が読みやすい
- 「淡色地図」を選んだのは、**上に情報を重ねる前提**だから。
  標準地図だと色が強く、投稿のピンやハザードの半透明が読みにくい

出典表示は地図右下と `/about` の 2 か所（`lib/credits.ts` が正本）。

## 11-3. なぜ PostgreSQL 17 か

**当初の計画では「DB を使わない」だった。** 住民と行政が投稿できる設計にした時点で
方針を変えた（`.agent/architecture.md` の「**方針変更**」）。

| 候補 | 判断 |
|---|---|
| **PostgreSQL 17（`postgres:17-alpine`）** | **採用** |
| SQLite | 不採用 |
| MySQL / MariaDB | 不採用 |
| 「DB を使わない」（JSON ファイル） | 不採用 |

**PostgreSQL を選んだ理由:**

1. **Docker 公式イメージ（DOI）がある。** 提出要件で DOI が推奨されている
2. **`jsonb` がある。** 3 カテゴリを 1 テーブルに統一する設計（11-5）は
   カテゴリ固有の項目を JSON で持てることが前提
3. **`normalize(text, NFKC)` が 13 以降の組み込み。** 全角半角をそろえた検索が
   拡張を入れずに書ける（[04 章 4-9](04-features.md#4-9-その他の機能)）
4. **`timestamptz` と `AT TIME ZONE` がある。** JST の暦日で絞る処理が SQL で書ける

**SQLite を選ばなかった理由**: 上の 2・3・4 がどれも弱い（`jsonb` 相当が無い、
NFKC 正規化が無い、タイムゾーン演算が弱い）。
また `docker compose` で「コンテナ 2 つ」を見せるほうが、
提出要件の「Docker コンテナの作成例」に沿う。

### なぜ PostGIS を入れないか

| 理由 | 詳細 |
|---|---|
| **DOI ではない** | PostGIS 入りイメージは公式イメージではない |
| **要るのは矩形検索と距離だけ** | 地図の表示範囲で絞る（`lat BETWEEN … AND lon BETWEEN …`）と、最寄りの点を探す（Haversine）の 2 つしか使わない |
| **規模が小さい** | 投稿は 1 市で数百件の想定。B-tree の索引で十分 |

距離計算は自前の Haversine（`lib/geo.ts`・`lib/jma.ts`）。**外部ライブラリも使わない**。

### なぜ ORM もマイグレーションツールも入れないか

- **依存とビルドリスクを増やさない。** `pg`（node-postgres）は純 JS で、
  ネイティブ拡張のビルドが起きない
- スキーマは `/docker-entrypoint-initdb.d` に SQL を置くだけで、
  **審査員の初回起動で確実にできる**。追加の手順が要らない
- 代償は「**スキーマを変えたら `docker compose down -v` が要る**」こと。
  開発期間が 1 か月強なので、マイグレーションの履歴管理より起動の確実さを優先した

## 11-4. なぜ写真を DB でなくファイルに置くか

**named volume（`uploads`）に実体、DB にはファイル名だけ。**

| 理由 | 詳細 |
|---|---|
| **DB の行が軽い** | 一覧（`GET /api/reports`）は最大 1000 件返す。1 枚 5 MB の bytea が混ざると転送も解析も重い |
| **配信をブラウザに任せられる** | `/api/photos/:id/:n` が `Cache-Control: public, max-age=86400` を付ける。2 回目以降はブラウザのキャッシュで済む |
| **バックアップの単位を分けられる** | 投稿データ（`db-data`）と写真（`uploads`）が別のボリューム |

**代償**: DB とファイルが食い違いうる。それを避けるため:

- 作成時は **1 トランザクション**で `reports` + `report_photos` を入れ、
  失敗したら**保存した写真を消す**（`api/reports/route.ts` の `savedFiles`）
- 削除時は **DB の行を消してから**実体を消す。
  消し損ねても DB の整合性は壊れない（孤児ファイルが残るだけ）

### 置き場のパスを環境変数にしない理由

```ts
const UPLOADS_SUBDIR = "uploads";
path.join(process.cwd(), UPLOADS_SUBDIR, fileName)
```

**Next.js のビルドはファイル操作のパスを静的に追う。**
追えないと「プロジェクト全体を出力に同梱する」動きになり、実行イメージが膨らむ
（実測でビルド警告 3 件。`.agent/architecture.md`）。
だから `path.join(process.cwd(), UPLOADS_SUBDIR, ...)` の形をそのまま書いている。

## 11-5. なぜ 3 カテゴリを 1 テーブル・1 API・1 フォームに統一するか

危険箇所（F-2）・浸水（F-3）・観光おすすめ（F-6）は、利用者から見れば
**「位置＋写真＋説明を投稿する」**という同じ操作。

| 分けた場合 | 統一した場合 |
|---|---|
| テーブル 3・API 3 本 ×5 メソッド・フォーム 3・地図レイヤー 3 組 | テーブル 1・API 1 本・フォーム 1・地図レイヤー 1 組 |
| カテゴリを増やすと全部増える | `REPORT_CATEGORIES` に**1 行足すだけ** |

**効き目の実例**: `ReportForm.tsx`（345 行）に**カテゴリ固有のコードは 1 行も無い**。
入力欄は `reportCategoryDef(category).detailFields` から組み立てる。
CSV の列も `REPORT_CATEGORIES` から自動で増える（`lib/reportExport.ts` の `DETAIL_COLUMNS`）。

**統一しない部分もある**（`requirements.md` §4）:
防災と観光を**同じ地図に同じ濃さで混ぜると読めなくなる**ので、
モード（S-1 / S-2）で「最初から表示する組」を分けている（[07 章 7-7](07-map.md#7-7-モードの切り替えs-1-防災--s-2-観光)）。

## 11-6. なぜ「予測」と言わないか（気象業務法）

**F-4 の注意案内は「浸水するでしょう」に類する予報表現を書かない。**
書いてよいのは次の 2 つの**事実**だけ。

1. 過去にこの地域で浸水報告が N 件あった（CHIZUBA に溜まった投稿）
2. 気象庁の予報では今後 24 時間に雨の見込みがある（気象庁の発表をそのまま引用）

### 根拠となる条文

**気象業務法（昭和二十七年法律第百六十五号）第十七条第一項**
（[e-Gov 法令検索](https://laws.e-gov.go.jp/law/327AC0000000165)。
2026-09-03 に e-Gov 法令 API v2 で条文を取得して確認）:

> （予報業務の許可）
> **第十七条** 気象庁以外の者が気象、地象、津波、高潮、波浪又は洪水の予報の業務
> （以下「予報業務」という。）を行おうとする場合は、**気象庁長官の許可を受けなければならない。**

CHIZUBA が独自の見通しを述べると、この許可制に触れうる。
**気象庁の発表を引用することと、自分で予報を出すことは別**なので、
引用に留める線を守っている。

### コードでの守り方

| 場所 | どう守っているか |
|---|---|
| `lib/weather.ts` の冒頭コメント | 「**予報表現を足さない**」と明記 |
| `components/FloodAlertCard.tsx` の冒頭コメント | 同上。「文言の制約（勝手に変えないこと）」 |
| 見出しの文言 | 「浸水報告のある地域に、**雨の予報が出ています**」（事実の並置） |
| `tidyForecastSummary()` | 気象庁の天気文を**全角スペースの半角化だけ**して引用。語は変えない |
| `buildFloodAlert()` | **予報が取れないときは注意を出さない**（根拠のない警告にしない） |

### 出典の書き方

気象庁の公共データ利用規約は「出典：気象庁ホームページ（URL）」の表記を求め、
**編集・加工して使うときは加工した旨も別に書く**ことになっている。
CHIZUBA は最寄り観測所の抽出と距離の計算をしているので、そこまで書いている
（`lib/credits.ts` の `DATA_CREDITS`）。

## 11-7. なぜデモログインを常設するか

**2 つの局面がある。**

### ① 鍵が無い環境（審査員）

Google の鍵を用意しないと**投稿機能を 1 つも試せない**のでは、
「実装した割合 × 動作する割合」の後者が 0 になる。
だから**鍵が無ければ自動でデモログインに落ちる**。

### ② 鍵がある環境（公開時）

以前は排他で、**鍵を入れるとデモログインが消えていた**。
それだと公開先で Google アカウントを持たない人が何も投稿できない。
そこで**鍵の有無は「Google を足すかどうか」だけに効かせる**ように変えた
（PR #21 `feat/google-demo-coexist`）。

**鍵が無い環境の見える DOM は 1 文（事実と食い違う案内文）以外そのまま**であることを、
main とのレンダリング差分で確認済み（`.agent/progress.md` 2026-08-30）。

### 公開時の穴と、その塞ぎ方

デモログインは**ロールを自己申告できる**ので、そのまま公開すると
通りすがりの誰でも行政ロールで入り、対応状況を書き換えられる。
`GOV_DEMO_PIN` を設定した環境だけ、**行政ロールにだけ** PIN を要求する
（[06 章 6-3](06-auth.md#6-3-デモログイン)）。

**一般ユーザーのログインには一切影響しない。** 守りたいのは
行政だけが持つ操作であって、投稿そのものではない。

## 11-8. なぜ公開 URL を設定値で持たないか

**固定値は「住所を変えたら設定も直す」を人間が覚えている前提で、実際に破れた。**

| いつ | 何が起きたか |
|---|---|
| 以前 | `compose.yaml` が `AUTH_URL=http://localhost:3000` を固定で渡していた |
| 事故 | `CHIZUBA_PORT=3100` で開いた人が、ログイン後に **3000 番へ飛ばされた** |
| Funnel 公開 | 設定し忘れると即「**ログインできない公開サイト**」になる |

そこで**リクエストが名乗ったホストから毎回導く**ことにした
（PR #18 `fix/auth-redirect-host`）。

### 実測でわかったこと（この修正の難しさ）

1. **`AUTH_URL` を外すだけでは直らない。** `output: "standalone"` の Next.js は
   待ち受けアドレス（`HOSTNAME=0.0.0.0`）からリクエスト URL を組むので、
   `/api/auth/*` に `http://0.0.0.0:3000/...` が渡り、リダイレクトが `0.0.0.0` になる
2. **経路によって URL の決め方が違う。** サーバーアクション（`signIn`/`signOut`）は
   `createActionURL()` がヘッダーを見るので `trustHost: true` だけで足りるが、
   ルートハンドラは `Auth()` が `req.url` を見るので**自分で直す**。
   片方だけ直すと気づきにくい
3. **`x-forwarded-port` は見てはいけない。** Next.js がコンテナ内のポート（3000）を
   無条件に入れる
4. **壊れた `X-Forwarded-Host` を弾いたあと `Host` に落とさないと `0.0.0.0` に戻る**

詳細は [06 章 6-6](06-auth.md#6-6-公開-url-の導出)。

## 11-9. なぜ Tailscale Funnel で公開するか

**発表とデモのために、審査員や来場者が自分のスマホから触れる状態を作る**のが目的。

| 候補 | 判断 |
|---|---|
| **Tailscale Funnel（自宅の Mac）** | **採用** |
| Vercel / Cloudflare Pages | 不採用 |
| VPS を借りる | 不採用 |

**Funnel を選んだ理由:**

- **提出物（`app/`）を 1 バイトも変えずに公開できる。** 常時稼働の差分は
  `deploy/selfhost/compose.prod.yaml` に分けてあり、
  審査員が `docker compose up` する経路には混ざらない
- **HTTPS 証明書（Let's Encrypt）が自動**。Google OAuth のコールバックに使える
- **無料・アカウント登録だけ**。VPS の費用とサーバー管理が要らない

**Vercel を選ばなかった理由**: PostgreSQL と写真のボリュームが要るので、
サーバーレスに載せると外部 DB とオブジェクトストレージの契約が必要になる。
**「認証キーが要る外部サービスを使わない」という前提が崩れる。**

### 実測でわかった落とし穴

- **`pmset` の `sleep 0` はアイドルスリープしか止めない。**
  画面スリープ→ダークウェイクに入ると Tailscale ごと 8 分間 offline になった。
  恒久対策は `sudo pmset -a sleep 0 disablesleep 1 displaysleep 0`
- **非対話 SSH の macOS の PATH に `/usr/local/bin` は無い。**
  Docker Desktop を入れてあっても `setup.sh` が「docker が見つかりません」で止まる
- **Funnel の URL は MagicDNS 配下では外部検証にならない。**
  tailnet 内から引くと 100.x が返るので、公開 DNS が返す ingress を
  `curl --resolve` で強制しないと「Tailscale 無しで開けるか」を確かめたことにならない

## 11-10. その他の判断（一覧）

`.agent/architecture.md`「設計判断の記録」より。

| 判断 | 結論 | 理由 |
|---|---|---|
| 実装言語・フレームワーク | Next.js（App Router）+ TypeScript | 地図 UI とサーバー側の中継 API を **1 コンテナに収められる** |
| ハザードマップ | **ラスタタイルを重ねる**（ポリゴンを DB に入れない） | 無認証。実装が最小になる |
| 経路サービス | OSRM（FOSSGIS） | 無認証。徒歩プロファイルあり |
| 気象データ | 気象庁 防災情報 JSON | 無認証。**一次情報であり出典として強い** |
| CSS | Tailwind CSS v4 | 提出までの期間が短く、書き足しの速度を優先 |
| アイコン | lucide-react | 依存ゼロの SVG コンポーネント。**絵文字は UI に使わない** |
| 配色 | [Okabe-Ito](https://jfly.uni-koeln.de/color/) | 色覚多様性に配慮した配色として国内で実績がある。**色だけに頼らず形でも区別する** |
| スキーマ投入 | `/docker-entrypoint-initdb.d` に SQL をマウント | 審査員の初回起動で確実にスキーマができる |
| 投稿写真の形式検査 | 申告 MIME に加えて**先頭バイトも見る** | 拡張子と Content-Type は書き換えられる |
| セッション | JWT ＋ インストール ID の縛り | テーブルとコードが 1 つ減る。ID を混ぜるのは実測で権限が通ってしまったため |
| 公開ポート | `${CHIZUBA_PORT:-3000}`（既定は動かさない） | 審査員の体験を変えずに、塞がっている環境だけ逃がせる |

## 11-11. UI の判断

### モバイルファースト

**このアプリはスマホから使う**（現場から危険箇所を報告する）。
新しい UI は **375px 幅で先に決めてから**広い画面へ広げ、
**375px で実際に動かして確かめる**（`.agent/conventions.md`）。

実測で直した破綻の例（PR #15・9 件）:

| 症状 | 原因と対処 |
|---|---|
| **初回表示で地図が 119px しか見えない** | 操作パネルが開いた状態で出ていた → 既定を「畳んだ状態」にし、地図を 514px に |
| **ピンを押してもポップアップがシートの裏で見えない** | MapLibre のポップアップは z-index を持たない → CSS で 15 を付与 |
| 320px で閉じるボタンが 45px 画面外へ | 投稿詳細のヘッダーが折り返せない → バッジ側だけ折り返す入れ物に |
| スライダーの当たり判定が 4px | `input[type="range"]` は**要素の高さがそのまま指の当たり判定** → `globals.css` で高さを確保 |

### 「押せるもの」の大きさ

画面上部の帯は 40px。**押せるものは帯いっぱいの高さと 40px 以上の幅を取る**
（`AuthBar.tsx` の `min-w-10 self-stretch`）。

### 帯の 3 段構え

| 幅 | 出るもの |
|---|---|
| 〜639px（スマホ） | ロゴマーク＋アイコンだけ（＋「デモモードで動作中」） |
| 640〜767px | ＋ ワードマーク `CHIZUBA` |
| 768px〜 | ＋ 投稿一覧・表示名・ログアウトの文字 |

**段を 1 つにまとめない。** まとめると全部が同時に現れる幅で余白が 10px まで詰まる（実測）。

## 11-12. 「デモ」を実データに見せない建付け

デモ投稿（22 件）が実際の通報と取り違えられると、防災の情報として害になる。
**4 重で示している。**

1. **`details.demo` フラグ**（`isDemoReport`）→ 一覧と詳細にバッジ
2. **本文の末尾に断り書き**（「※ CHIZUBA の動作確認のために用意したデモ投稿です」）
3. **浸水の雨量は「デモ用のダミー値」とだけ表示**し、気象庁出典を出さない
4. **書き出し（CSV / GeoJSON）にも `is_demo` 列を出し、雨量は出さない**

**利用者はデモバッジを詐称できない。** `parseDetails` がカテゴリ定義外のキーを
捨てるので、`demo: true` を送っても 201 の応答に `demo` が入らない（実測で確認）。

写真も**再利用可のものだけ**で、**防災の 7 枚は市外の参考写真**である旨を
`/about` に明記している。

## 11-13. 判断の記録がどこにあるか
