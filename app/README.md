# CHIZUBA — 千葉の地図に、住民と行政の「いま」を重ねる

**CHIZUBA**（チズバ。**CHI**ba + **ZU**（地図）+ **BA**（場））は、千葉県の地図系サービスを
1 つに束ね、**住民と行政が相互に情報を投稿できる**ウェブサイトです。

ハザードマップと市のオープンデータ（避難場所・AED・子育て施設・景観100選）を地図に重ね、
その上に住民の**危険箇所の報告**・**冠水の報告**・**観光のおすすめ**を載せます。
行政は投稿に**公式コメント**を付け、**対応状況**を 4 段階で更新できます。
**閲覧はログイン不要**で、投稿とコメントにだけログインが要ります。

対応範囲は千葉県全域（市町村コードでパラメータ化）、**デモデータは市川市**です。

> ### 審査員の方へ
>
> - **追加の設定は要りません。** `docker compose up` だけで、投稿・コメント・
>   **行政ロールの操作まで含めて全機能**を試せます（[2 章](#2-ログイン)）。
> - Google の認証キーは同梱していません。キーが無い環境では**自動でデモログインに切り替わる**
>   ので、そのまま使えます。理由は [2-4](#2-4-認証キーを同梱していない理由)。
> - **起動直後から投稿が 22 件入っています**（[4 章](#4-起動直後から入っているデモ投稿)）。
>   空の地図では投稿機能の様子が分からないためで、画面では「デモ投稿」の印を付けて区別しています。
> - **読んでいただきたいのは 1〜7 章です。** 8 章から先はチーム内の開発メモです。
> - このファイルは補足で、提出要件の `readme.txt` が本体です。内容は一致させてあります。

## 1. 動かす

### 1-1. 必要なもの

| | 内容 |
|---|---|
| **必須** | **Docker Desktop**（または Docker Engine）。`docker compose` サブコマンドが使える版 ＝ **Compose V2 以降** |
| **必須** | **インターネット接続。** 背景地図・ハザードマップ・徒歩経路・気象データは外部サービスを参照します（**認証キー・アカウントはすべて不要**） |
| 不要 | Node.js・PostgreSQL・API キー・アカウント登録。**コンテナの外に用意するものはありません** |

動作を確認した環境: **Docker 29.7.2 / Docker Compose v5.3.1**（macOS 15・Apple Silicon）。
ベースイメージ（`node:22-slim` / `postgres:17-alpine`）はどちらも
**linux/amd64 と linux/arm64 の両方**が配信されているので、
Intel Mac・Windows・Apple Silicon のいずれでも追加の指定なしにビルドできます。

**時間の目安**（手元の実測）:

| | 時間 |
|---|---|
| ベースイメージの取得（初回のみ） | 合計約 760 MB。回線しだいで数分 |
| `docker compose up` のビルド | **約 15 秒**（キャッシュ無しで計測。`npm ci` 5.7 秒 ＋ `npm run build` 5.3 秒） |
| 起動 → `http://localhost:3000` が応答 | **約 7 秒**（DB のスキーマ流し込みを含む） |

### 1-2. 起動

作業ディレクトリ（この README がある場所）で:

```bash
docker compose up
```

ビルドと起動が終わったらブラウザで <http://localhost:3000> を開きます。
止めるときは、そのターミナルで `Ctrl-C`。

コンテナは 2 つ立ちます。

| コンテナ | 中身 |
|---|---|
| `web` | サービス本体（Next.js。`node:22-slim` の multi-stage ビルド） |
| `db` | PostgreSQL 17（`postgres:17-alpine`）。住民と行政の投稿を保存します |

`web` は `db` の healthcheck が通るまで起動しません（`depends_on: service_healthy`）。
テーブルは `db` の初回起動時に `db/init/*.sql` が自動で流れるので、
**データ投入の手順はありません**。

> **`db` はホストにポートを公開していません。** 審査員の環境で 5432 番が
> 埋まっていても起動できるようにするためです。

### 1-3. 止める・作り直す

```bash
docker compose down                 # 止めて片付ける（投稿は残る）
docker compose down -v              # ＋ データベースと投稿写真も消す（最初の状態に戻る）
docker compose down --rmi local     # ＋ ビルドしたイメージも消す
docker compose up --build           # コードを変えたあとビルドし直す
```

**`-v` を付けると、投稿・ユーザー・投稿写真がすべて消え、デモ投稿が入り直します。**
「最初の状態に戻したい」ときはこれを使ってください。
ログイン状態も無効になります（理由は [8 章](#8-既知の制約とその理由)の `AUTH_SECRET` の項）。

### 1-4. 3000 番が塞がっているとき

公開ポートだけを変えられます。**他に直す設定はありません。**

```bash
CHIZUBA_PORT=3100 docker compose up   # → http://localhost:3100
```

`.env` に `CHIZUBA_PORT=3100` と 1 行書いても同じです。

ログイン後のリダイレクト先も Google のコールバック URL も、
**ブラウザが実際に開いた住所から毎回決まります**（`src/lib/publicOrigin.ts`）。
ポートを変えても、リバースプロキシや HTTPS 越しに出しても、設定を足す必要はありません。

## 2. ログイン

**閲覧にログインは要りません。** 地図・ハザードマップ・投稿の閲覧・投稿一覧・
CSV / GeoJSON の書き出しは、ログインなしで全部使えます。
ログインが要るのは**投稿とコメント**だけです。

ログイン方法は **2 つ**あり、**デモログインは常に使えます**。

| 方法 | 必要なもの | 既定 |
|---|---|:--:|
| **デモログイン** | 表示名を入れるだけ | **常に使える** |
| **Google ログイン** | Google Cloud の OAuth クライアント（任意） | キーを設定した環境だけ |

### 2-1. デモログイン（追加設定なし・審査はこれだけで完結します）

1. 画面右上の **「ログイン」** を押す（または <http://localhost:3000/login>）
2. **表示名**を入れる（本名でなくてかまいません。例: `審査員`）
3. **ロール**を選ぶ — **「一般ユーザー」** か **「行政ユーザー（市川市）」**
4. **「デモログイン」** ボタンを押す

パスワードもアカウント登録も要りません。
ログアウトは画面右上の「ログアウト」です。

同じ「表示名 × ロール」で入り直すと**同じユーザー**として扱われるので、
自分の投稿を編集・削除する動きもそのまま試せます。

> **キーが無い環境ではログイン画面にデモログインだけが出ます。**
> 実測: `GET /api/auth/providers` → `{"demo": {...}}` のみ。

### 2-2. 行政ユーザーを試す

**ログイン画面で「行政ユーザー（市川市）」を選ぶだけです。PIN も承認も要りません。**
審査員が `docker compose up` だけで行政側の機能まで試せるように、そうしてあります。

行政ユーザーで入ると、次の 2 つができるようになります。

| できること | 場所 |
|---|---|
| **対応状況の更新**（未対応 → 受付 → 対応中 → 対応済） | 投稿のピンを押して開く詳細パネルの中 |
| **公式コメント** | 同じ詳細パネルのコメント欄。行政の発言は「行政の公式回答」として区別表示されます |

更新できるのは**担当する市町村（市川市 = `12203`）の投稿だけ**です。
一般ユーザーが対応状況を変えようとすると拒否されます（実測: HTTP 403
`この投稿の対応状況を変更する権限がありません。`）。

> **インターネットに公開するときだけ**、`.env` に `GOV_DEMO_PIN` を書くと
> 行政ユーザーを選ぶときに PIN を要求するようになります（一般ユーザーのログインは変わりません）。
> **審査には関係ありません。未設定のままにしてください。**

### 2-3. Google ログイン（任意）

**試していただく必要はありません**が、確かめたい場合の手順です。所要 5 分ほど。

1. <https://console.cloud.google.com/apis/credentials> で
   **「認証情報を作成」→「OAuth クライアント ID」**、種類は **「ウェブ アプリケーション」**
2. **「承認済みのリダイレクト URI」** に、**実際にブラウザで開く住所**に
   `/api/auth/callback/google` を付けたものを登録する

   ```
   http://localhost:3000/api/auth/callback/google
   ```

   `CHIZUBA_PORT` を変えたなら、そのポートで登録してください（例: `http://localhost:3100/...`）
3. 発行された 2 つの値を、この作業ディレクトリ直下に `.env` を作って書く

   ```bash
   # .env
   GOOGLE_CLIENT_ID=<発行されたクライアント ID>
   GOOGLE_CLIENT_SECRET=<発行されたクライアントシークレット>
   ```
4. 読み込ませるために立て直す

   ```bash
   docker compose up -d       # 既に起動中なら、これで web だけ作り直されます
   ```

これで `/login` に **Google とデモログインの両方**が並びます。
**キーを入れてもデモログインは消えません**（Google アカウントを持たない人も入れるようにするため）。

実測（ダミーのキーで確認）:

- `GET /api/auth/providers` → `google` と `demo` の 2 つ
- Google のボタンから `https://accounts.google.com/o/oauth2/v2/auth` へ 302
- そのときの `redirect_uri` は `http://localhost:<開いたポート>/api/auth/callback/google`
  （**ポートを変えても自動で追従します**）

Google で入った人のロールは**自己申告できません**。行政ロールを付けるには
`.env` に `GOV_ACCOUNTS=メールアドレス:12203` の形で書きます（`.env.example` 参照）。

### 2-4. 認証キーを同梱していない理由

**クライアントシークレットを配布物に入れると、秘密情報を公開することになるため**です。
zip は複数人の手に渡り、開発リポジトリは public です。
その代わりに、**キーが無い環境では自動でデモログインに落ちる**構成にしてあり、
デモログインでも**投稿・コメント・行政ロールの操作まで、審査対象の機能はすべて同じように動きます**。

Google ログインが実際に動くところは、[6 章](#6-公開デモ)の公開デモで確認できます。

## 3. 何ができるか — 画面のどこを見ればいいか

画面は**地図 1 枚**が中心です。ヘッダーのすぐ下のタブで
**防災マップ**と**観光マップ**を切り替えます（地図は作り直されません）。

### 3-1. 機能と場所の対応

| 機能 | どこで見られるか |
|---|---|
| **ハザードマップ**（洪水・高潮・津波の浸水想定と、土砂災害警戒区域） | 防災マップ → 操作パネル最下部「ハザードマップ（浸水・土砂災害）」。**洪水は最初から重なっています**（不透明度 60%）。**土砂災害（急傾斜地の崩壊）は既定 OFF**で、押すと重なります。凡例と出典も同じ場所 |
| **施設のオープンデータ** | 操作パネル「表示するデータ」。指定緊急避難場所 123・AED 設置箇所 304・子育て施設 388・景観100選 100 をトグルで出し入れ。点を押すと名称・所在地・種別が出ます |
| **危険箇所の報告** | 防災マップの橙のピン。押すと詳細パネル（写真・本文・コメント・対応状況） |
| **冠水の報告 ＋ 投稿時点の雨量** | 防災マップの青のピン。詳細に**投稿した瞬間の 1 時間降水量**が、**観測所名と距離つき**で入っています |
| **注意案内** | 防災マップの操作パネル最上部。**過去に浸水報告がある地域に雨の予報が出ているとき**だけ出ます（事実 2 つを並べるだけで、浸水の予測はしません） |
| **観光マップ・景観100選** | 「観光マップ」タブ。点を押すと**日本語と英語の解説**・アクセス方法が読め、そのまま徒歩ナビの目的地にできます。**100 か所のうち 54 か所に写真**が付きます |
| **観光おすすめの投稿** | 観光マップの赤紫のピン |
| **行政からの応答** | 投稿の詳細パネル。**「行政の公式投稿」バッジ**と、地図では**青い輪のピン**。公式コメントと対応状況は行政ユーザーで入ると操作できます（[2-2](#2-2-行政ユーザーを試す)） |
| **徒歩ナビ** | 操作パネル「徒歩ナビ」→「現在地から最寄りの地点へ」。現在地が取れないときは「出発地点を地図で指定する」。ポップアップの「ここへナビ」で任意の地点も選べます |
| **投稿する** | ログイン後、操作パネルの「みんなの投稿」に出る黒いボタン。**いま見ているモードのカテゴリぶんだけ**並びます（防災マップは「危険箇所を投稿する」「浸水を投稿する」、観光マップは「観光おすすめを投稿する」）。位置・写真（3 枚まで）・本文・カテゴリ固有の項目を入れます |
| **投稿一覧** | ヘッダーの「投稿一覧」（<http://localhost:3000/reports>）。カテゴリ・期間・キーワードで絞り込み |
| **オープンデータとして書き出す** | 操作パネルと投稿一覧の「オープンデータとして持ち帰る」→ **CSV / GeoJSON**。**絞り込んだ条件のまま**出ます |
| **キーワード検索・期間の絞り込み・現在地** | 操作パネルの「検索」「期間でしぼる」と、地図右上の現在地ボタン |
| **出典とライセンス** | 地図の隅（短い版）と <http://localhost:3000/about>（全件） |
| **プライバシーポリシー** | <http://localhost:3000/privacy> |

### 3-2. 操作パネルの並び（防災マップ）

上から順に、こう並んでいます。**スマホ幅では下から引き上げるシート**になります。

1. **注意案内**（条件が揃ったときだけ）
2. **検索** — 投稿のタイトル・本文と、景観スポットの名前から探す
3. **表示するデータ** — 避難場所 / AED / 子育て施設 / 景観100選のトグル
4. **みんなの投稿** — 「一覧で見る」・**投稿ボタン**（未ログインなら「投稿するにはログイン」、
   ログイン後は「危険箇所を投稿する」「浸水を投稿する」）・**いまの雨量**（観測所名と距離つき。
   防災マップだけ）・危険箇所 / 浸水 / 観光おすすめのトグル
5. **期間でしぼる** — すべて / 今日 / 7 日間 / 30 日間、または開始日と終了日
6. **オープンデータとして持ち帰る** — CSV / GeoJSON
7. **徒歩ナビ**
8. **ハザードマップ（浸水・土砂災害）** — 洪水 / 高潮 / 津波 / 土砂災害のトグルと不透明度、
   **凡例**（浸水は深さ、土砂災害は区域の種別）、
   「色が付いていない場所が安全とは限りません」の注意書き、出典
9. **出典 / プライバシー**へのリンク

### 3-3. おすすめの見て回り方（5 分）

1. `docker compose up` → <http://localhost:3000>。**洪水の浸水想定が重なった市川市の地図**が出ます
   （地図タイルと点の描画に数秒かかります）
2. 橙のピンをどれか押す → 写真・本文・**対応状況**・コメントが読めます
3. 青のピン（浸水）を押す → **投稿時点の雨量**が観測所名と距離つきで入っています
4. 右上の**「ログイン」→ 表示名を入れて「行政ユーザー（市川市）」→「デモログイン」**
5. さっきの投稿をもう一度開く → **対応状況を変えられ、コメントが「行政の公式回答」になります**
6. ヘッダー下の**「観光マップ」**タブ → 景観100選の点を押すと解説と写真
7. 操作パネルの **CSV / GeoJSON** → 投稿がオープンデータとして落ちてきます

## 4. 起動直後から入っているデモ投稿

空の地図では投稿機能の様子が伝わらないので、`db/init/003_seed_demo_reports.sql` が
**22 件**の投稿を入れています（`db` の初回起動時だけ）。

| 内訳 | 件数 |
|---|---|
| 危険箇所 | **7 件** |
| 浸水 | **5 件**（**3 つの「雨のあった日」に散らしてあります** — 期間の絞り込みを試せるように） |
| 観光おすすめ | **10 件** |
| うち行政の公式投稿 | 3 件 |
| 写真が付いている投稿 | 16 件（写真は計 17 枚） |
| コメントが付いている投稿 | 6 件（うち公式コメント 3 件） |
| 対応状況 | 未対応 18・受付 2・対応中 1・対応済 1 |

**すべて実際の通報ではありません。**

- 画面では**「デモ投稿」バッジ**で区別し、本文の末尾にも断り書きを入れています
- **実際に起きた災害の被害を「ここで起きた」と書いた投稿は 1 件もありません。**
  場所は市内に散らした架空の地点です
- **浸水投稿の雨量はダミー値**です。過去の実測値は気象庁の JSON から取れないので、
  観測値のふりをさせていません（画面にも「デモ用のダミー値」と出ます。
  **CSV / GeoJSON の書き出しにも含めていません**）
- 写真は**再利用が許されたものだけ**（ウィキメディア・コモンズの CC0 / CC BY / CC BY-SA）。
  **防災の 7 枚は市外で撮られた参考写真**で、市川市の被害写真ではありません。
  作者とライセンスは <http://localhost:3000/about> に全件並べています

デモ投稿が要らなければ、`db/init/003_seed_demo_reports.sql` を**消してから**作り直します。

```bash
rm db/init/003_seed_demo_reports.sql
docker compose down -v && docker compose up
```

## 7. うまく動かないとき

### 3000 番が塞がっている

```
Error response from daemon: ports are not available:
exposing port TCP 0.0.0.0:3000 -> ... bind: address already in use
```

公開ポートを変えてください。**他に直す設定はありません**（[1-4](#1-4-3000-番が塞がっているとき)）。

```bash
docker compose down
CHIZUBA_PORT=3100 docker compose up   # → http://localhost:3100
```

### 地図は出るが、施設の点やピンが出ない

**まず数秒待ってください。** 地図タイルと点の描画は、ページが出たあとに非同期で進みます
（手元では 2〜4 秒）。

それでも出ない場合は、**インターネットに出られているか**を確認してください。
背景地図（国土地理院）・ハザードマップ・徒歩経路（OSRM）は外部サービスを参照します。
プロキシや社内ネットワークの制限で遮られていることがあります。

### ビルドが途中で失敗する

```bash
docker compose build --no-cache    # キャッシュを捨ててやり直す
docker compose up
```

`npm ci` が失敗する場合は、npm レジストリ（`registry.npmjs.org`）に出られるかを確認してください。

### Apple Silicon / Intel / Windows の違い

ベースイメージ（`node:22-slim` / `postgres:17-alpine`）はどちらも
**linux/amd64 と linux/arm64 の両方**が配信されているので、**プラットフォームの指定は要りません**。
`--platform` を手で足すと、かえって遅いエミュレーションになります。

### スキーマを変えたのに反映されない / 最初の状態に戻したい

`db/init/*.sql` は**データボリュームが空のときだけ**流れます（`postgres` イメージの仕様）。

```bash
docker compose down -v && docker compose up
```

**`-v` は投稿写真も一緒に消します。**

### ログインしていたのに、いつのまにか未ログインになる

`docker compose down -v` でデータベースを作り直すと、
**セッションの署名鍵の元になるインストール ID も変わる**ため、それ以前のログイン状態は無効になります
（作り直したのだから、投稿もユーザーも消えています）。詳しくは [8 章](#8-既知の制約とその理由)。

### 「データベースに接続できていません」と出る

`db` コンテナが立ち上がりきっていないか、落ちています。

```bash
docker compose ps          # db が healthy になっているか
docker compose logs db     # 起動ログ
```

**地図と施設の点と経路は、`db` が落ちていても表示されます**
（オープンデータは GeoJSON として同梱してあり、DB を経由しないため）。
使えなくなるのは投稿とログインだけです。

## 8. 既知の制約とその理由

- **インターネット接続が要る。** 背景地図（国土地理院）・ハザードマップ（ハザードマップ
  ポータルサイト）・徒歩経路（OSRM）・雨量と雨の予報（気象庁）は外部サービスを参照する。
  **認証キーやアカウントは不要**。
  経路サービスにつながらないときは直線距離と徒歩 4.8 km/h からの概算に切り替え、
  「経路を取得できませんでした」と画面に出す（無反応で止まることはない）。
  背景地図が出ない場合も、施設の点と経路は表示される
- **雨量は「最寄りのアメダスの値」であって、その地点の実測値ではない。**
  市川市にはアメダスが無く、**市の中心から最寄りの船橋まで約 10 km**（実測 10.2 km）ある。
  局地的な豪雨は数 km で降り方が変わるので、画面には**観測所名と距離を必ず添えて**出している。
  **選ばれる観測所は場所ごとに違う**（市の南部からは江戸川臨海が最寄りになる）。
  最寄りが 20 km 以上離れている地点では雨量を出さない
- **気象庁につながらないときも浸水報告は投稿できる。**
  雨量は空欄になり、詳細に「投稿時の雨量: 取得できませんでした」と出る。
  同じとき、**注意案内（過去の浸水報告 × 雨の予報）は出ない**
  （予報が取れないのに注意を出すと根拠のない警告になるため）
- **雨の予報は市町村単位では出ない。** 気象庁の府県天気予報は千葉県を
  「北西部 / 北東部 / 南部」の 3 区分で出しているので、注意案内には予報区名を併記している
- **現在地の取得は `localhost` か HTTPS でのみ動く**（ブラウザの仕様）。
  `docker compose up` 後に `http://localhost:3000` を開けば問題ない。
  取得できない・許可されない場合は「地図をクリックして出発地点を指定」に自動で切り替わる
- 経路サービス（FOSSGIS の OSRM）の利用規約に合わせ、**サーバー側で 1 秒あたり 1 リクエスト**に
  制限している。連続で押すと少し待たされることがある
- **MapLibre v6 の Web Worker は `public/maplibre/` に配置している。**
  v6 から worker が別ファイルになり、バンドルすると自分の場所を見つけられなくなったため、
  `scripts/copy-maplibre-worker.mjs` が `node_modules` からコピーし、
  `setWorkerUrl()` でそこを指している。**このコピーが無いと、背景地図は出るのに
  施設の点が永久に出ない**（`src/components/MapView.tsx` のコメント参照）。
  このディレクトリは配布物には含まれず、**`docker compose up` のビルド中に作り直される**
- **ハザードマップは「色が付いていない = 安全」ではない。** 想定区域が公表されていない
  河川・地域があり、その場所のタイルは配信されていない（HTTP 404 が返り、地図には何も
  描かれない）。この誤読を防ぐため、凡例に注意書きを常時出している
- **重ねているのは 4 種類だけで、「他の災害が無い」という意味ではない。**
  洪水・高潮・津波の浸水想定と、土砂災害警戒区域（急傾斜地の崩壊）を重ねられる。
  土砂災害は**市川市に 142 区域**が指定されていて（すべて急傾斜地の崩壊）、
  斜面のある北部に偏っているので**既定は OFF**にしてある。区域数の出典は
  [千葉県「土砂災害警戒区域等の一覧」](https://www.pref.chiba.lg.jp/kakan/sabou/keikai/)
  （同ページからたどれる「指定数及び指定箇所一覧等」の Excel に、市町村別の指定数がある）。
  内水（雨水出水）の浸水想定は市川市でも水防法にもとづいて指定・公表されているが、
  **公表されているのは PDF だけ**で、地図に重ねられる形では配信されていない。
  土石流と地すべりの警戒区域は市川市に指定が無い。
  同じ断りを `/about` にも出している（**文言を変えるなら両方**）
- **ハザードタイルの配信はズーム 2〜17。** それより拡大すると、17 のタイルを引き伸ばして
  表示する（新しい情報は増えない）。浸水深は段階ごとの色なので、拡大しても中間色が
  できないように最近傍で描画している。
  逆に**ズーム 6 より引くと重ねを描かない**（想定区域が数ピクセルの染みにしかならず、
  読めないタイルを取りに行き続けることになるため）。ズーム 6 で本州全体が入るので、
  千葉県内を見ているかぎり消えることはない
- **洪水と、津波・高潮では浸水深の段階が違う**（洪水は 6 段階、津波・高潮は 8 段階で、
  同じ色でも表す深さが違う）。凡例は重ねている想定に合わせて出し分けている
- 町丁字の境界ポリゴンは市川市オープンデータに無いので、面ではなく点で表示している
- **`db/init/*.sql` はデータボリュームが空のときだけ流れる**（`postgres` イメージの仕様）。
  スキーマを変えたら `docker compose down -v` でボリュームごと作り直す。
  変えていないのに反映されないときは、たいていこれが原因。
  **`-v` は投稿写真（`uploads` ボリューム）も一緒に消す**
- **投稿写真は `uploads` ボリューム（コンテナの `/app/uploads`）に置く。**
  `Dockerfile` で先に作って `node` 所有にしてある。これをやらないと
  ボリュームが root 所有になり、`USER node` で動くアプリが書き込めない。
  中を覗くときは `docker compose exec web ls -l /app/uploads`
- **投稿できる写真は JPEG / PNG / WebP、1 枚 5 MB まで、1 投稿 3 枚まで**
  （1 リクエスト全体で 10 MB まで）。拡張子と Content-Type は書き換えられるので、
  **サーバー側でファイルの先頭バイトも確かめている**。タイトルは 60 文字・
  説明は 1000 文字・コメントは 500 文字まで
- **投稿の市町村は座標から決める。** クライアントが送ってきた市町村コードは使わない
  （詐称を防ぐため）。市町村マスタの範囲から外れた座標は投稿できない
- **`db` はホストにポートを公開していない。** 審査員のマシンで 5432 が埋まっていても
  起動できるようにするため。中を覗くときは
  `docker compose exec db psql -U chizuba -d chizuba`
- **Google ログインは認証キーが要る**ので、既定ではデモログインだけで動く。
  キーを設定した環境では **Google とデモの両方**がログイン画面に並ぶ
  （`.env.example` 参照）。**公開する住所やポートを変えたときは、
  Google 側に登録するリダイレクト URI をその住所に合わせる**
  （`https://<住所>/api/auth/callback/google`）。
  **`.env` に `AUTH_URL` を書く必要は無い**（公開 URL はリクエストから毎回導く）
- **デモログインの「行政ユーザー」は、既定では誰でも選べる。** 審査員が
  `docker compose up` だけで行政側の機能（対応状況の更新・公式コメント）まで
  試せるようにするための建付け。**インターネットに公開するときだけ** `.env` に
  `GOV_DEMO_PIN` を書くと、行政ユーザーを選ぶときに PIN を要求するようになる
  （未設定なら何も変わらない。`.env.example` 参照）
- **公開 URL の設定は要らない。** ログイン後のリダイレクト先も Google の
  コールバック URL も、リクエストの `X-Forwarded-Host` →（無ければ）`Host` から
  毎回導く（`src/lib/publicOrigin.ts`）。だから `CHIZUBA_PORT` で公開ポートを
  変えても、リバースプロキシや Tailscale Funnel の HTTPS 越しに出しても、
  そのまま動く。**`AUTH_URL` を設定するとそちらが優先される**ので、
  ホスト名を書き換えてしまうプロキシの後ろに置くときだけ書く
  （書いたら、公開 URL を変えるたびに直す必要がある）
- **`AUTH_SECRET` は未設定でよい。** 未設定のときは、データベースに 1 つだけ入っている
  **インストール ID から署名鍵を導く**ので、環境ごとに違う鍵になる（`src/lib/installId.ts`）。
  トークンにも同じ ID が入っていて毎回突き合わせるため、
  **別の場所で動いている CHIZUBA のログイン状態は通らない**
  （Cookie はポートを区別しないので、同じ `localhost` の別インスタンス同士でも起きうる）。
  `docker compose down -v` でデータベースを作り直すと ID も変わり、それ以前の
  ログイン状態は無効になる（作り直したのだから、投稿もユーザーも消えている）
- **ロゴは `src/app/icon.svg` が正本。** `favicon.ico` と `apple-icon.png` はそこから起こしてある。
  作り直すときは `rsvg-convert` で書き出す（`apple-icon.png` は **角丸を外して透過なし**にする。
  iOS が自前で角丸マスクを掛けるうえ、透過は黒で埋められるため）。
  画面の中で使うロゴは `src/components/BrandMark.tsx` に同じ図形を写してあるので、
  **図形を変えたら SVG とコンポーネントの両方を直す**（タブと画面でロゴが食い違うと台無しになる）
- **画面上部の帯は 3 段構えで文字を出す。** 〜639px はロゴマークとアイコンだけ、
  640px からワードマーク、768px から投稿一覧・表示名・ログアウトの文字。
  **段を 1 つにまとめない**（全部が同時に現れる幅で余白が 10px まで詰まる）。
  「デモモードで動作中」は要件で文言が決まっていて縮められないので、幅は他から作る
- **`compose.yaml` はプロジェクト名を `ichikawa-opendata-map` に固定している**（審査員が
  ディレクトリ名に左右されず起動できるようにするため）。**プロダクト名 CHIZUBA と
  食い違っているのは意図的**で、名前を変えると起動中のコンテナが別プロジェクト扱いになり、
  作り直しになるため据え置いている（起動や採点には影響しない）。その分、同じマシンで複数の
  `docker compose` 操作を並行させると同じプロジェクトを取り合い、相手のコンテナを作り直したり
  落としたりしてしまう。**並行させるときは `docker compose -p 別の名前 …` で名前を分ける**

## 9. 手元で開発する（チーム向け）

毎回 Docker をビルドし直すのは遅いので、UI をいじるときは手元で Next.js を動かす
（保存すると自動で画面に反映される）。**Node.js 22 以上**が要る。

```bash
npm install
npm run dev                # http://localhost:3000
```

`npm run dev` / `npm run build` の前に `scripts/copy-maplibre-worker.mjs` が自動で走り、
MapLibre の Web Worker を `public/maplibre/` に配置する（[8 章](#8-既知の制約とその理由)参照）。

| コマンド | 何をするか |
|---|---|
| `npm run dev` | 開発サーバー（ホットリロードあり） |
| `npm run build` | 本番ビルド。Docker の中でも同じものが走る |
| `npm run typecheck` | TypeScript の型チェックだけ |

`npm run dev` は手元の Node.js で動くので、そのままだと `db` コンテナへ届かない
（`db` はホストにポートを公開していない）。地図まわりだけなら DB 無しで動き、
`/login` に「データベースに接続できていません」と出るだけ。
**ログイン・投稿・コメントを手元で試したいとき**は、`compose.yaml` の `db` に
一時的に `ports: - "5432:5432"` を足して起動し、接続先を渡す。

```bash
docker compose up -d db
DATABASE_URL=postgres://chizuba:chizuba_local_only@localhost:5432/chizuba npm run dev
```

**デモ投稿の写真は `npm run dev` では出ない。** 写真を `uploads/` に配っているのは
`Dockerfile`（`db/seed-photos/` → `/app/uploads`）なので、手元で見たいときは自分でコピーする。

```bash
mkdir -p uploads && cp db/seed-photos/*.jpg uploads/
```

地図に載せる GeoJSON を作り直すときは、開発リポジトリのルートで
`python3 data/scripts/build_geojson.py`（**この配布物には含まれない**。開発リポジトリ側にある）。

**PostGIS も ORM もマイグレーションツールも入れていない**（緯度経度は数値カラム）。

## 11. 提出物を作る（チーム向け）

> このディレクトリ配下が、そのまま提出 zip になる。
> **提出要件の正本は、開発リポジトリの `課題/2026-09-09_CODIHA2026_提出要件.md`**
> （**この配布物には含まれない**）。このファイルと食い違ったら、課題 md を正とする。

### 絶対に守るルール

#### 1. ファイル名に日本語を使わない

**この配下のファイル名・ディレクトリ名はすべて英数字**（`_` `-` は可）にする。
提出要件で明確に禁止されている。
開発リポジトリ直下の `課題/` は zip に含めないので日本語名のままでよい。
**この線引きを崩さない**（提出対象をこのディレクトリの外に置かない・中に日本語名を作らない）。

#### 2. `docker compose up` で動くこと

審査員は Docker で動作確認する。**コードは
「必要な機能に対して実装した割合 × 正しく動作する割合」の掛け算**で採点されるので、
**動かない機能を積むより、動く機能を確実に仕上げるほうが点になる。**

- ベースイメージは可能な限り **Docker 公式イメージ（DOI）**、タグを固定する（`latest` を使わない）
- 審査員の環境に無いもの（外部 API のキー、手元のデータファイル）が無いと動かない構成にしない

#### 3. 氏名・所属を含む `readme.txt` はコミットしない

**開発リポジトリは public。** `readme.txt` には提出者の氏名と所属を書く必要があるが、
それを public リポジトリの履歴に入れてはいけない。
**`readme.txt` は `.gitignore` 済み。** 提出直前に手元で作り、zip に入れて提出する。

### `readme.txt` に書く内容

プレーンテキスト・**UTF-8（BOM なし）**。

ヘッダ（前書き）:

- Slack のチームチャンネル名（**正確に書き写す**）
- 提出者の氏名と所属（日本語で姓名、大学 / 学部・コース名）

本文（番号付き。**該当しない項目は「なし」と書く**）:

1. 概要・主要機能（**必須**。説明資料 1 と齟齬のないように）
2. 使用しているポート番号（ホスト OS からコンテナに接続する場合のみ）→ **3000**
3. ログイン情報（コンテナ接続時に必要な場合のみ）
   → **このサービスでは「デモログイン」の手順を書く**。
   「閲覧にログインは不要。投稿を試すときは画面右上の『ログイン』から、
   表示名を入れて『一般ユーザー』か『行政ユーザー（市川市）』を選ぶ。
   パスワードやアカウントの用意は不要」という趣旨を、審査員が迷わない粒度で書く
4. 実行方法（**必須**。`docker compose up` など起動方法を正確に。説明資料 1 と齟齬のないように）

末尾に特記事項・補足（起動時に審査員が注意すべき事項）。

**`compose.yaml` のポート番号と `readme.txt` の記載は必ず一致させる。**
このファイルの [1 章](#1-動かす)・[2 章](#2-ログイン)とも一致させる。

### 提出アーカイブを作る

**手で固めない。** 開発リポジトリの `tools/package_submission.sh` が
クリーンコピー → 7z 化 → 展開し直しての検証まで一気にやる。
提出物に不備があると採点されないので、手作業で取りこぼす余地を残さない。

```bash
# 開発リポジトリのルートで
bash tools/package_submission.sh                 # dist/ai-de-chiba-map.7z ができる
bash tools/package_submission.sh our-team-name   # ベース名を変えたいとき（英数字と . _ - のみ）
bash tools/package_submission.sh --smoke         # ＋ 展開先で実際に起動して HTTP 200 まで見る
bash tools/package_submission.sh --smoke --smoke-port 3200   # 3000 が塞がっているとき
```

やってくれること:

- `node_modules/` `.next/` `tsconfig.tsbuildinfo` などを落としてこのディレクトリをコピーする
  （`.gitignore` の判定をそのまま使う。ただし `readme.txt` は gitignore 済みでも必ず入れる）
- ベース名のディレクトリへリネームしてから 7z で固める（7z が無ければ zip）
- 固めたアーカイブを**展開し直し**、そこに対して下の項目を確認する

| 自動で見る項目 | 落ちたときの意味 |
|---|---|
| `readme.txt` がある | 提出必須ファイルが無い |
| `readme.txt` が UTF-8・BOM なし | 提出要件どおりの文字コードでない |
| `Dockerfile` `compose.yaml` がある | 提出必須ファイルが無い |
| 展開すると作業ディレクトリが 1 つだけできる | ベース名の付け方が違う |
| 日本語（非 ASCII）のファイル名が無い | 提出要件で禁止されている |
| キャッシュ・ビルド生成物の混入が無い | 提出要件で削除を指示されている |
| 展開し直した中身が固める前と一致する | アーカイブが壊れている |
| 展開先で `docker compose config` が通る | 審査員の環境で起動できない |
| 展開先で `docker compose up` が HTTP 200 を返す（`--smoke` のときだけ） | 審査員の環境で起動できない |

1 つでも落ちたら、**作ったアーカイブを消して**非 0 で終了する
（不備のあるものを誤って提出しないため）。出力の `[ NG ]` を直してもう一度実行する。
