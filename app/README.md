# app — CHIZUBA（提出するサービス本体）

**このディレクトリ配下が、そのまま提出 zip になる。**

**CHIZUBA**（**CHI**ba + **ZU**（地図）+ **BA**（場））は、千葉県の地図系サービスを
1 つに束ね、**住民と行政が相互に情報を投稿できる**ウェブサイト。
**対応は千葉県全域で、デモデータは市川市**。何を作るかの正本は
[`../docs/design/requirements.md`](../docs/design/requirements.md)。

CODIHA 2026 のコード提出は「**作業ディレクトリ丸ごとの zip（または 7z）**」なので、
審査員に渡すものは全部ここに入れ、渡さないものはここに入れない。

提出要件の正本は [`../課題/2026-09-09_CODIHA2026_提出要件.md`](../課題/2026-09-09_CODIHA2026_提出要件.md)。
このファイルと食い違ったら、**課題 md を正とする**。

> この `README.md` は開発用のメモ。審査員が読むのは後述の `readme.txt` のほう。

## 動かす

**必要なのは Docker Desktop だけ**（Node.js を入れる必要はない）。

```bash
cd app
docker compose up          # 初回はイメージのビルドで数分かかる
```

起動したらブラウザで <http://localhost:3000> を開く。止めるときは `Ctrl-C`。
コードを変えたあとは `docker compose up --build` でビルドし直す。

```bash
docker compose down                 # 片付け
docker compose down -v              # ＋ データベースの中身も消す
docker compose down --rmi local     # イメージごと消す
```

コンテナは **`web`（サービス本体）と `db`（PostgreSQL 17）の 2 つ**。
`web` は `db` の healthcheck が通るまで起動しない（`depends_on: service_healthy`）。
テーブルは初回起動時に `db/init/*.sql` が自動で流れるので、投入の手順は要らない。
**このとき、デモ投稿が 22 件（防災 12・観光 10）入る。** 空の地図では投稿機能の
様子が分からないので、住民の投稿・行政の公式投稿・コメント・対応状況が
最初から入った状態にしてある。**実際の通報ではない**ので、画面では
「デモ投稿」の印を付けて区別している（消したいときは下の「デモ投稿を消す」を参照）。

**ログインは何も用意しなくても使える。** Google の認証キーが無い環境では
自動でデモログインに切り替わり、表示名を入れるだけで一般ユーザーにも
行政ユーザーにもなれる（`/login`）。

### 中身を書き換えながら開発する

毎回 Docker をビルドし直すのは遅いので、UI をいじるときは手元で Next.js を動かす
（保存すると自動で画面に反映される）。**Node.js 22 以上**が要る。

```bash
cd app
npm install
npm run dev                # http://localhost:3000
```

`npm run dev` / `npm run build` の前に `scripts/copy-maplibre-worker.mjs` が自動で走り、
MapLibre の Web Worker を `public/maplibre/` に配置する（後述の「既知の制約」参照）。

| コマンド | 何をするか |
|---|---|
| `npm run dev` | 開発サーバー（ホットリロードあり） |
| `npm run build` | 本番ビルド。Docker の中でも同じものが走る |
| `npm run typecheck` | TypeScript の型チェックだけ |

`npm run dev` は手元の Node.js で動くので、そのままだと `db` コンテナへ届かない
（`db` はホストにポートを公開していない）。地図まわりだけなら DB 無しで動き、
`/login` に「データベースに接続できていません」と出るだけ。
**ログイン・投稿・コメントを手元で試したいとき**は、`compose.yaml` の `db` に
一時的に `ports: - "5432:5432"` を足して起動し、接続先を渡す。

```bash
docker compose up -d db
DATABASE_URL=postgres://chizuba:chizuba_local_only@localhost:5432/chizuba npm run dev
```

**デモ投稿の写真は `npm run dev` では出ない。** 写真を `uploads/` に配っているのは
`Dockerfile`（`db/seed-photos/` → `/app/uploads`）なので、手元で見たいときは自分でコピーする。

```bash
mkdir -p uploads && cp db/seed-photos/*.jpg uploads/
```

### デモ投稿を消す

デモ投稿は `db/init/003_seed_demo_reports.sql` が入れている。要らなければ
**このファイルを消してから**データベースを作り直す（`db/init/` はボリュームが
空のときだけ流れるので、消すだけでは既に入ったぶんは消えない）。

```bash
rm db/init/003_seed_demo_reports.sql
docker compose down -v && docker compose up
```

### 地図に載せるデータを作り直す

`public/data/*.geojson` は市川市の CSV から生成したもの。元データを更新したら作り直す。

```bash
# リポジトリのルートで
python3 data/scripts/build_geojson.py
```

## 何ができるか

- **起動した直後から投稿が入っている**: デモ投稿が 22 件（危険箇所 7・浸水 5・観光 10）
  あり、写真・コメント・対応状況（未対応／受付／対応中／対応済）も付いている。
  **実際の通報ではない**ので「デモ投稿」バッジで区別し、本文にも断りを書いている。
  写真は再利用が許されたものだけで、作者とライセンスは `/about` に並べてある
- **ハザードマップ**: 洪水・高潮・津波の**浸水想定区域**を地図に重ねる。
  想定ごとに表示の ON/OFF と不透明度を変えられ、浸水深の凡例と出典が出る
  （初期状態では洪水だけ重ねてある）
- 市川市の**指定緊急避難場所 123 件・AED 設置箇所 304 件・子育て施設 388 件**を地図に重ねる。
  レイヤーごとに表示を切り替えられ、点をクリックすると名称・所在地・種別ごとの詳細が出る
- **防災マップと観光マップを、ヘッダー直下のタブで切り替えられる**（`/` と `/?mode=tourism`）。
  切り替わるのは**最初から表示するレイヤーの組と、投稿できるカテゴリ**だけで、地図は 1 枚のまま。
  切り替えたあとに個別のレイヤーを足し引きするのは自由
- **行政の投稿は一目で分かる**。一覧と詳細に「行政の公式投稿」バッジが出て、
  地図ではピンの輪が公式色（青）になる。観光おすすめは住民と行政の両方が投稿できる
- 市川市の**景観100選 100 件**を観光モードで重ねる。点をクリックすると
  **日本語と英語の解説**・アクセス方法が読め、そのまま徒歩ナビの目的地にできる。
  カテゴリ（まち並み・自然・歴史・文化・生活風景）で色分けする。
  **100 か所のうち 54 か所には写真が付く**（ウィキメディア・コモンズの再利用可能なもの。
  作者とライセンスはポップアップに出し、全部の一覧は `/about` にある）
- **徒歩ナビ**: 現在地（または地図で指定した地点）から、表示中のレイヤーで最も近い地点までの
  徒歩経路を引き、距離と所要時間の目安を出す。ポップアップの「ここへナビ」で任意の地点も選べる
- **住民・行政の投稿**: 危険箇所（壊れたガードレール・陥没した路面など）と
  **冠水している場所**を、**位置 + 写真 + 説明**で投稿できる。地図にピンが出て、
  クリックすると詳細パネルが開き、写真・説明・コメントが読める。コメントは誰でも付けられ、
  **行政ユーザーの発言は「行政の公式回答」として区別表示**される。
  投稿者は自分の投稿を削除できる。
  **閲覧はログイン不要で、投稿とコメントにだけログインが要る**
- **浸水報告の雨量**: 冠水の投稿には、**投稿した瞬間の 1 時間降水量が自動で記録**される。
  値は気象庁のアメダス実況から取り、**観測所名と距離を添えて**出す
  （その地点の実測値ではないため）。雨量は投稿者が入力・改変できない
- **注意案内**: 雨の予報が出ているとき、**過去に浸水の報告があった地点**に注意表示を出す。
  出すのは「過去に N 件の浸水報告がある」「気象庁の予報で降水確率が最大 X%」という
  **事実 2 つだけ**で、浸水の予測はしない
- **投稿一覧**（`/reports`）: 新着順のリスト。カテゴリで絞り込め、選ぶと地図のその投稿が開く
- **ログイン**（`/login`）: 投稿機能のための土台。Google ログインが本線で、
  認証キーが未設定の環境では**自動でデモログイン**になる。デモでは表示名を入れるだけで入れ、
  「一般ユーザー」と「行政ユーザー（市川市）」を選べる。**閲覧にログインは要らない**

## 構成

```
app/
├── Dockerfile            multi-stage（依存の取得 → ビルド → 実行）
├── compose.yaml          docker compose up 用。web と db の 2 コンテナ
├── .env.example          環境変数の名前と説明（値は書かない。実値は .env へ）
├── db/init/              スキーマ・市町村マスタ・デモ投稿。db の初回起動時に流れる
├── db/seed-photos/       デモ投稿の写真 17 枚。ビルド時に uploads/ へ配られる
├── scripts/              ビルド前に走る補助スクリプト
├── public/data/          市川市オープンデータから作った GeoJSON 4 本
├── uploads/              投稿写真の実体（起動時に作られる。コンテナでは named volume）
└── src/
    ├── app/              画面（/ = 地図、/reports = 投稿一覧、/login、/about）と API
    │   ├── icon.svg          ロゴの正本（タブアイコン）
    │   ├── favicon.ico       SVG ファビコンを読めないブラウザ向けの控え（16/32/48）
    │   └── apple-icon.png    ホーム画面追加用（180px・角丸なし・透過なし）
    ├── components/       地図・操作パネル・投稿フォーム・詳細パネル・経路カード・通知・ヘッダー
    ├── lib/              レイヤー定義・景観スポット・地図のモード・ベースマップ・
    │                     距離計算・出典・DB・認証・投稿
    └── types/            外部ライブラリの型の拡張
```

| 使っているもの | 何のために |
|---|---|
| Next.js（App Router）+ TypeScript | 画面と、経路サービスへの中継 API |
| MapLibre GL JS | 地図の描画。認証キー不要 |
| Tailwind CSS + lucide-react | 見た目とアイコン |
| 国土地理院「淡色地図」タイル | 背景地図。認証キー不要 |
| ハザードマップポータルサイト（国土交通省） | 洪水・高潮・津波の浸水想定タイル。認証キー不要 |
| OSRM（FOSSGIS e.V. 提供） | 徒歩経路の計算。認証キー不要 |
| PostgreSQL 17（`postgres:17-alpine`） | 住民・行政の投稿とユーザーの保存 |
| named volume `uploads` | 投稿写真の実体。DB にはファイル名だけを記録する |
| Auth.js（NextAuth）+ `pg` | ログインと DB 接続。ORM は入れていない |

**地図に載せるオープンデータは DB を経由しない。** GeoJSON として同梱してあるので、
`db` が落ちていても地図と施設の点と経路は出る（投稿とログインだけが使えなくなる）。

## 既知の制約

- **インターネット接続が要る。** 背景地図（国土地理院）・ハザードマップ（ハザードマップ
  ポータルサイト）・徒歩経路（OSRM）・雨量と雨の予報（気象庁）は外部サービスを参照する。
  **認証キーやアカウントは不要**。
  経路サービスにつながらないときは直線距離と徒歩 4.8 km/h からの概算に切り替え、
  「経路を取得できませんでした」と画面に出す（無反応で止まることはない）。
  背景地図が出ない場合も、施設の点と経路は表示される
- **雨量は「最寄りのアメダスの値」であって、その地点の実測値ではない。**
  市川市にはアメダスが無く、最寄りの船橋まで約 10 km ある。局地的な豪雨は数 km で
  降り方が変わるので、画面には**観測所名と距離を必ず添えて**出している。
  最寄りが 20 km 以上離れている地点では雨量を出さない
- **気象庁につながらないときも浸水報告は投稿できる。**
  雨量は空欄になり、詳細に「投稿時の雨量: 取得できませんでした」と出る。
  同じとき、**注意案内（過去の浸水報告 × 雨の予報）は出ない**
  （予報が取れないのに注意を出すと根拠のない警告になるため）
- **雨の予報は市町村単位では出ない。** 気象庁の府県天気予報は千葉県を
  「北西部 / 北東部 / 南部」の 3 区分で出しているので、注意案内には予報区名を併記している
- **現在地の取得は `localhost` か HTTPS でのみ動く**（ブラウザの仕様）。
  `docker compose up` 後に `http://localhost:3000` を開けば問題ない。
  取得できない・許可されない場合は「地図をクリックして出発地点を指定」に自動で切り替わる
- 経路サービス（FOSSGIS の OSRM）の利用規約に合わせ、**サーバー側で 1 秒あたり 1 リクエスト**に
  制限している。連続で押すと少し待たされることがある
- **MapLibre v6 の Web Worker は `public/maplibre/` に配置している。**
  v6 から worker が別ファイルになり、バンドルすると自分の場所を見つけられなくなったため、
  `scripts/copy-maplibre-worker.mjs` が `node_modules` からコピーし、
  `setWorkerUrl()` でそこを指している。**このコピーが無いと、背景地図は出るのに
  施設の点が永久に出ない**（`app/src/components/MapView.tsx` のコメント参照）
- **ハザードマップは「色が付いていない = 安全」ではない。** 想定区域が公表されていない
  河川・地域があり、その場所のタイルは配信されていない（HTTP 404 が返り、地図には何も
  描かれない）。この誤読を防ぐため、凡例に注意書きを常時出している
- **ハザードタイルの配信はズーム 2〜17。** それより拡大すると、17 のタイルを引き伸ばして
  表示する（新しい情報は増えない）。浸水深は段階ごとの色なので、拡大しても中間色が
  できないように最近傍で描画している。
  逆に**ズーム 6 より引くと重ねを描かない**（想定区域が数ピクセルの染みにしかならず、
  読めないタイルを取りに行き続けることになるため）。ズーム 6 で本州全体が入るので、
  千葉県内を見ているかぎり消えることはない
- **洪水と、津波・高潮では浸水深の段階が違う**（洪水は 6 段階、津波・高潮は 8 段階で、
  同じ色でも表す深さが違う）。凡例は重ねている想定に合わせて出し分けている
- 町丁字の境界ポリゴンは市川市オープンデータに無いので、面ではなく点で表示している
- **`db/init/*.sql` はデータボリュームが空のときだけ流れる**（`postgres` イメージの仕様）。
  スキーマを変えたら `docker compose down -v` でボリュームごと作り直す。
  変えていないのに反映されないときは、たいていこれが原因。
  **`-v` は投稿写真（`uploads` ボリューム）も一緒に消す**
- **投稿写真は `uploads` ボリューム（コンテナの `/app/uploads`）に置く。**
  `Dockerfile` で先に作って `node` 所有にしてある。これをやらないと
  ボリュームが root 所有になり、`USER node` で動くアプリが書き込めない。
  中を覗くときは `docker compose exec web ls -l /app/uploads`
- **投稿できる写真は JPEG / PNG / WebP、1 枚 5 MB まで、1 投稿 3 枚まで**
  （1 リクエスト全体で 10 MB まで）。拡張子と Content-Type は書き換えられるので、
  **サーバー側でファイルの先頭バイトも確かめている**。タイトルは 60 文字・
  説明は 1000 文字・コメントは 500 文字まで
- **投稿の市町村は座標から決める。** クライアントが送ってきた市町村コードは使わない
  （詐称を防ぐため）。市町村マスタの範囲から外れた座標は投稿できない
- **`db` はホストにポートを公開していない。** 審査員のマシンで 5432 が埋まっていても
  起動できるようにするため。中を覗くときは
  `docker compose exec db psql -U chizuba -d chizuba`
- **Google ログインは認証キーが要る**ので、既定ではデモログインで動く。
  キーを設定した環境だけが Google モードになり、両方が欠けていればデモモードに戻る
  （`.env.example` 参照）。**`ports` のホスト側を 3000 から変えたときは、
  `.env` に `AUTH_URL` を書いて Google 側に登録した URI とそろえる**
- **`AUTH_SECRET` は未設定でよい。** 未設定のときは、データベースに 1 つだけ入っている
  **インストール ID から署名鍵を導く**ので、環境ごとに違う鍵になる（`src/lib/installId.ts`）。
  トークンにも同じ ID が入っていて毎回突き合わせるため、
  **別の場所で動いている CHIZUBA のログイン状態は通らない**
  （Cookie はポートを区別しないので、同じ `localhost` の別インスタンス同士でも起きうる）。
  `docker compose down -v` でデータベースを作り直すと ID も変わり、それ以前の
  ログイン状態は無効になる（作り直したのだから、投稿もユーザーも消えている）
- **ロゴは `src/app/icon.svg` が正本。** `favicon.ico` と `apple-icon.png` はそこから起こしてある。
  作り直すときは `rsvg-convert` で書き出す（`apple-icon.png` は **角丸を外して透過なし**にする。
  iOS が自前で角丸マスクを掛けるうえ、透過は黒で埋められるため）。
  画面の中で使うロゴは `src/components/BrandMark.tsx` に同じ図形を写してあるので、
  **図形を変えたら SVG とコンポーネントの両方を直す**（タブと画面でロゴが食い違うと台無しになる）
- **画面上部の帯は 3 段構えで文字を出す。** 〜639px はロゴマークとアイコンだけ、
  640px からワードマーク、768px から投稿一覧・表示名・ログアウトの文字。
  **段を 1 つにまとめない**（全部が同時に現れる幅で余白が 10px まで詰まる）。
  「デモモードで動作中」は要件で文言が決まっていて縮められないので、幅は他から作る
- **`compose.yaml` はプロジェクト名を `ichikawa-opendata-map` に固定している**（審査員が
  ディレクトリ名に左右されず起動できるようにするため）。**プロダクト名 CHIZUBA と
  食い違っているのは意図的**で、名前を変えると起動中のコンテナが別プロジェクト扱いになり、
  作り直しになるため据え置いている（起動や採点には影響しない）。その分、同じマシンで複数の
  `docker compose` 操作を並行させると同じプロジェクトを取り合い、相手のコンテナを作り直したり
  落としたりしてしまう。**並行させるときは `docker compose -p 別の名前 …` で名前を分ける**
  （`tools/package_submission.sh` の検証は `-p pkgtest-<PID>` で隔離してある）

## 🚫 絶対に守るルール

### 1. ファイル名に日本語を使わない

**この配下のファイル名・ディレクトリ名はすべて英数字**（`_` `-` は可）にする。
提出要件で明確に禁止されている。

リポジトリ直下の `課題/` は zip に含めないので日本語名のままでよい。
**この線引きを崩さない**（提出対象を `app/` の外に置かない・`app/` の中に日本語名を作らない）。

### 2. `docker compose up` で動くこと

審査員は Docker で動作確認する。**コードは
「必要な機能に対して実装した割合 × 正しく動作する割合」の掛け算**で採点されるので、
**動かない機能を積むより、動く機能を確実に仕上げるほうが点になる。**

- ベースイメージは可能な限り **Docker 公式イメージ（DOI）**、タグを固定する（`latest` を使わない）
- 審査員の環境に無いもの（外部 API のキー、手元のデータファイル）が無いと動かない構成にしない

### 3. 氏名・所属を含む `readme.txt` はコミットしない

**このリポジトリは public。** `readme.txt` には提出者の氏名と所属を書く必要があるが、
それを public リポジトリの履歴に入れてはいけない。

**`app/readme.txt` は `.gitignore` 済み。** 提出直前に手元で作り、zip に入れて提出する。

## 提出アーカイブを作る

**手で固めない。** [`../tools/package_submission.sh`](../tools/package_submission.sh) が
クリーンコピー → 7z 化 → 展開し直しての検証まで一気にやる。
提出物に不備があると採点されないので、手作業で取りこぼす余地を残さない。

```bash
# リポジトリのルートで
bash tools/package_submission.sh                 # dist/ai-de-chiba-map.7z ができる
bash tools/package_submission.sh our-team-name   # ベース名を変えたいとき（英数字と . _ - のみ）
bash tools/package_submission.sh --smoke         # ＋ 展開先で実際に起動して HTTP 200 まで見る
bash tools/package_submission.sh --smoke --smoke-port 3200   # 3000 が塞がっているとき
```

やってくれること:

- `node_modules/` `.next/` `tsconfig.tsbuildinfo` などを落として `app/` をコピーする
  （`.gitignore` の判定をそのまま使う。ただし `readme.txt` は gitignore 済みでも必ず入れる）
- ベース名のディレクトリへリネームしてから 7z で固める（7z が無ければ zip）
- 固めたアーカイブを**展開し直し**、そこに対して下の項目を確認する

| 自動で見る項目 | 落ちたときの意味 |
|---|---|
| `readme.txt` がある | 提出必須ファイルが無い |
| `readme.txt` が UTF-8・BOM なし | 提出要件どおりの文字コードでない |
| `Dockerfile` `compose.yaml` がある | 提出必須ファイルが無い |
| 展開すると作業ディレクトリが 1 つだけできる | ベース名の付け方が違う |
| 日本語（非 ASCII）のファイル名が無い | 提出要件で禁止されている |
| キャッシュ・ビルド生成物の混入が無い | 提出要件で削除を指示されている |
| 展開し直した中身が固める前と一致する | アーカイブが壊れている |
| 展開先で `docker compose config` が通る | 審査員の環境で起動できない |
| 展開先で `docker compose up` が HTTP 200 を返す（`--smoke` のときだけ） | 審査員の環境で起動できない |

1 つでも落ちたら、**作ったアーカイブを消して**非 0 で終了する
（不備のあるものを誤って提出しないため）。出力の `[ NG ]` を直してもう一度実行する。
