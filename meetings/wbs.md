# WBS（Work Breakdown Structure）

プロジェクトの作業分解表。**このファイルを埋めるのが最初の仕事**。

粒度は 1 タスク = 数時間〜数日（長くても 3 日程度）が目安。
細かすぎると管理が面倒になり、粗すぎると進捗が見えなくなる。

> **Issue と結びつけると回り始める。**
> WBS の 1 行 = GitHub Issue 1 件にして、番号を「Issue」列に書き戻す。
> 手順は [CONTRIBUTING.md の 8. Issue で作業を管理する](../CONTRIBUTING.md#8-issue-で作業を管理する) を参照。

## ヒント

- タスク名は「動詞＋対象」で具体的に（例: 「〇〇機能を実装」）
- 依存関係を明記すると、並行作業できるタスクが見えてくる
- 工数は楽観的に見積もらない（経験則: 最初の見積もりの 1.5〜2 倍はかかる）
- **「状態」列は毎週のミーティングで必ず更新する。** 更新されない WBS は誰も見なくなる
- コードを書くタスクだけでなく、**報告書・発表・議事録・評価**も行に入れる。
  これらを入れ忘れると終盤に一気に押し寄せる
